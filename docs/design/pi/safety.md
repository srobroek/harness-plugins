## Gate-by-gate: cc-safety-net coverage

“Full” below means it enforces the same practical gate, not necessarily identical internal logic. “Partial” means it recognizes some of the same command shapes but differs materially in target coverage, state proof, or allow/ask behavior. The safety plugin’s shell walk is documented in `plugins/safety/opencode/src/shell.ts:1-8,90-170`; its hard gates are in `guards.ts:339-383`, and its Git risk review in `permission.ts:183-210`.

| Our gate | cc-safety-net coverage | Evidence / important difference |
|---|---|---|
| `rm -rf` and destructive filesystem commands | **Partial.** It has path-sensitive rules for recursive deletes, Git metadata, `find`, `rsync`, disk writes, and related operations. It does **not** block every literal `rm -rf` under default standard mode. Dynamic targets are blocked in strict; recursive deletes within the working directory are blocked when paranoid-rm is enabled. | Its [filesystem rules](https://ccsafetynet.com/docs/reference/blocked-commands#filesystem-commands) and [mode defaults](https://ccsafetynet.com/docs/configuration/modes#default-mode) document those levels. Our hard gate blocks an unverified expansion on destructive operands (`guards.ts:78-112`); it is not a blanket literal `rm -rf` gate. |
| `git reset --hard` | **Partial.** Recognized and blocked by default; optional linked-worktree mode relaxes it. It does not probe whether the reset is a no-op, fast-forward, or would lose commits/dirty tracked work. | Rule `git.reset-hard` in [`destructive.ts`](https://github.com/kenryu42/cc-safety-net/blob/main/src/core/rules/destructive.ts); [worktree-mode behavior](https://ccsafetynet.com/docs/configuration/modes#worktree-mode-cc_safety_net_worktree=1). Our plugin asks only when its probes see risk (`permission.ts:78-85,183-210`). |

## Parser approach: source and test read

CC’s POSIX parser is a syntax-aware command parser, not a regex over the full string. Its source models words/provenance, groups, functions, nested programs, redirects, heredocs, and connectors in [`src/core/shell/posix.ts`](https://github.com/kenryu42/cc-safety-net/blob/main/src/core/shell/posix.ts). The analyzer then unwraps wrappers and recurses into supported shell/interpreter execution paths (`src/gate/analyzer/wrapper-prelude.ts`, `src/gate/analyzer/shell-execution.ts`).

| Case | Finding |
|---|---|
| Quoting | **Handled.** The parser preserves quoting/provenance and separates quoted data from command structure. Some unusual or unsupported syntax may still be unresolved; strict mode denies unparseable commands. |
| Subshells / groups | **Handled for parsed groups and nested substitutions.** |
| Chained commands | **Handled.** Commands are parsed as separate segments; destructive rules analyze the segments, not just the first command. |
| Environment prefixes | **Handled.** Leading `NAME=value` assignments are stripped into environment context; `env` options and `env -S` have dedicated handling. |
| `command` / `builtin` wrappers | **Handled.** `wrapper-prelude.ts` explicitly peels both, as well as `sudo` and `env`. |
| `git -C` | **Handled.** `-C` is a recognized Git global option and worktree analysis resolves its directory. See [`src/core/rules/constants.ts`](https://github.com/kenryu42/cc-safety-net/blob/main/src/core/rules/constants.ts) and [`src/gate/analyzer/git/worktree.ts`](https://github.com/kenryu42/cc-safety-net/blob/main/src/gate/analyzer/git/worktree.ts). |
| Aliases | **Shell aliases are not generally resolved.** It does block Git’s inline `git -c alias.*=…` dangerous-alias configuration, but that is not alias expansion from shell startup state. The docs also warn that unsupported/opaque wrappers can hide commands. |

Our parser comparison is based on reading the implementation and its tests; **I did not install or run these packages in Pi**.

## Pi install and configuration recipe

The documented Pi integration is an **in-process extension wired to `tool_call`**. The Pi adapter handles `bash` and `powershell` as command tools; non-command Pi tools still receive sensitive-path inspection. It is not a Pi MCP proxy or external hook. See [Pi installation](https://ccsafetynet.com/docs/installation/pi) and [`src/hosts/pi/tool-call.ts`](https://github.com/kenryu42/cc-safety-net/blob/main/src/hosts/pi/tool-call.ts).

1. Install cc-safety-net through the managed setup. Dotfiles provide its rulebooks and policy on Pi and OMP, load it before our extension, and leave it unpinned.

## Pick one and preserve the other layers

- **Pick cc-safety-net over `@spences10/pi-confirm-destructive`** if the priority is broad, deterministic hard denials and secret-path protection. The two overlap on destructive shell calls. cc-safety-net does not ask; the confirmer does, and uses Git recoverability evidence. Running both without a deliberate policy split risks redundant prompts and blocks; a confirmer’s approval cannot make a separate hard-deny hook allow the call.
- **Pick `@spences10/pi-confirm-destructive` over cc-safety-net** if the priority is asking before a risky operation and allowing it once/session, especially when Git state can prove the operation safe. It is not a replacement for CC’s secret-path checks or strict parser policy.
- **Use `@gotgenes/pi-permission-system` as a separate policy layer**, not as a destructive-policy preset. It can provide Pi-wide tool/path/MCP/skill and ask/deny policy; custom bash rules can overlap either package. Avoid broad PIS `bash: "*": "ask"` rules for commands CC already blocks unless that extra prompt is intended.

## Keep our own plugin, and watch duplication in other harnesses

Host-specific gates moved to private configuration.

Where cc-safety-net is installed in another supported harness, overlapping rules may duplicate detections. Keep one authoritative policy per behavior, or disable an overlapping rule after validating the replacement.

## Unverified

- I did not install, execute, or integration-test any package in Pi. The Pi wiring and parser findings above are source/docs inspection.
- No evidence reviewed establishes an exact Pi runtime peer-version requirement for cc-safety-net; its package has a Pi extension manifest but no declared Pi peer range.
- Secret-path coverage is a bounded rule catalog, not general filesystem containment; CC documents exceptions and limits in its [secret reference](https://ccsafetynet.com/docs/reference/secret-protection) and [known limitations](https://ccsafetynet.com/docs/guides/known-limitations).
- `@spences10/pi-confirm-destructive` download counts differ between the npm downloads API and Pi’s catalog; both values are reported above.
- Parser gaps, alias behavior, and interaction between multiple Pi tool-call extensions should be validated in the user’s actual Pi extension set before making cc-safety-net the sole destructive-action gate.
