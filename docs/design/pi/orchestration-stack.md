# Orchestration stack decision

**Decision: use `pi-subagents` as the one Pi fan-out runtime.** The distinction is not “scripts versus no scripts”: current `pi-subagents` also has scripted workflows. It is whether you want a highly controlled generated-JavaScript workflow engine or one broader delegation runtime that also owns agent definitions, run recovery, Herdr integration, and Worktrunk-backed worktrees.

[Workflows](https://github.com/nicobailon/pi-subagents/blob/main/docs/workflows.md) · [agents](https://github.com/nicobailon/pi-subagents/blob/main/docs/agents.md) | Their public tool/command names differ, so they can be loaded together, but they do not compose into one runtime. Co-loading creates two competing orchestration surfaces, not “Dynamic Workflows on top of subagents.” |

**Verdict: skip as a second active runtime.** Dynamic Workflows is a viable standalone alternative if script-first, resumable review/research workflows become the priority. It is not a plug-in frontend for `pi-subagents`, and its Worktrunk fit is weaker for your setup.

## Recommended stack

- **Fan-out:** `pi-subagents` only. Use its scripted workflows for explicit multi-step runs; keep child keys stable. Set `worktreeProvider: "auto"` (or `"worktrunk"` if you want fail-closed behavior) and leave worktree integration/merge-back to the existing reviewed flow. [Workflows](https://github.com/nicobailon/pi-subagents/blob/main/docs/workflows.md) · [Worktrunk configuration](https://github.com/nicobailon/pi-subagents/blob/main/docs/configuration.md)
- **Project persistence/goal:** no additional autonomous-goal package by default. Keep **Beads** as the project issue authority and use `pi-subagents` missions as execution/run records, not as a competing backlog. Missions are durable and do not themselves schedule or restart children. [Missions](https://github.com/nicobailon/pi-subagents/blob/main/docs/missions.md)
- **Communication:** adopt `pi-intercom` for separate Pi sessions; use `pi-subagents`’ native supervisor channel for its own workers. This assigns each channel a different audience.
- **Memory:** retain the current Mnemopi/Obsidian arrangement until you verify that Pi lacks access to the knowledge it needs. Trial Engram only as a deliberate shared-memory replacement, not a second auto-capture store.
- **Keep out of the default stack:** Dynamic Workflows, pi-herdsman, pi-loop, pi-goal and pi-background-tasks for now. Herdsman is the one worth revisiting if you need managed Lead/Manager projects; pi-goal is the one to test separately if you need one session to keep pursuing a goal automatically.
- **Conflicts to avoid:** two agent-fan-out runtimes; an active `pi-goal` alongside subagent work without a shared mutex; a second memory database with overlapping contents; and treating Worktrunk allocation as proof that branches have been reviewed or merged.
