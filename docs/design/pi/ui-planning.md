# UI, planning and interaction

**Recommendation:** Keep **Parley** for questions and approval rounds. Use **`@narumitw/pi-plan-mode`** as the primary Pi plan workflow, and trial **Plannotator** for browser-based reviews and annotations, not as a second active plan controller. For the footer, use **one owner**: I recommend **`@narumitw/pi-statusline`**, with Herdr retaining agent-state display.

## Parley vs. `@juicesharp/rpiv-ask-user-question`

| Feature | Parley | `rpiv-ask-user-question` |
|---|---|---|
| Multi-question interaction | Up to **12** questions in one round; later questions can join an open round. (`plugins/parley/opencode/src/questions.ts:32`; `tui.tsx:221-229`) | Up to **4** questions in one questionnaire with a Submit review tab. ([tool schema](https://github.com/juicesharp/rpiv-mono/blob/main/packages/rpiv-ask-user-question/docs/tool-schema.md)) |
| Typed answers | Pick-one/many, free text/code, confirm, slider/rate, review/diff, file/image, and structured forms/ranges/dates/tags, among other kinds. (`questions.ts:4-25`, `answers.ts:61-177`) | Single/multi-select and free-text; **no typed number/slider**. A number can be typed as text but is not validated as numeric. ([tool schema](https://github.com/juicesharp/rpiv-mono/blob/main/packages/rpiv-ask-user-question/docs/tool-schema.md)) |
| Recommendations | Structured recommendation initializes an answer and can be explicitly accepted; accepting is distinguished from choosing another value. (`questions.ts:220-243`; `answers.ts:195-209`) | No recommendation field or default selection contract. Instructions say put the recommended option first and label it `(Recommended)`. ([README](https://github.com/juicesharp/rpiv-mono/blob/main/packages/rpiv-ask-user-question/README.md)) |
| Notes | Per-question notes; a note-only answer is a distinct state. (`answers.ts:8-9,183-194`) | Per-question and global notes in TUI; **no notes through RPC/ACP dialogs**. ([hosts](https://github.com/juicesharp/rpiv-mono/blob/main/packages/rpiv-ask-user-question/docs/hosts.md)) |
| Deferral | Explicit `deferred` state and pending IDs; unanswered questions can remain open. (`answers.ts:189-191`; `index.ts:27-29`) | No defer answer. Esc cancels the questionnaire; Submit can leave questions blank and reports them unanswered. ([tool schema](https://github.com/juicesharp/rpiv-mono/blob/main/packages/rpiv-ask-user-question/docs/tool-schema.md)) |
| Previews | Supports rich question content and review/diff/file/image surfaces; it does **not** provide the ask package’s side-by-side preview for each option. (`questions.ts:35-78`) | Markdown preview per option, **single-select only**. ([tool schema](https://github.com/juicesharp/rpiv-mono/blob/main/packages/rpiv-ask-user-question/docs/tool-schema.md)) |
| Persistence / compaction | Round records and delivery state are stored; open rounds expire after 24 hours. (`persist.ts:10-31,106-107`) | No persisted open-question recovery across compaction is documented; treat that behavior as unsupported. |
| RPC / headless | OpenCode has RPC routes and can fall back to the host’s `question` tool when no Parley UI is attached. (`plugins/parley/opencode/src/index.ts:123-166`; `plugins/parley/opencode/src/service.ts:29-42,1054-1063`) | RPC/ACP uses sequential native dialogs, without TUI notes/previews/review tab; in headless runs the tool is removed from the model’s tool list. ([hosts](https://github.com/juicesharp/rpiv-mono/blob/main/packages/rpiv-ask-user-question/docs/hosts.md)) |
| Subagent-to-user forwarding | Includes session-scoped round delivery and synthetic messages that wake/resume the session. (`index.ts:75-80`; `service.ts:186-191,814-920`) | Inbound answer events let external programs answer a questionnaire, but the event bus is per session; it does not itself forward a child agent’s question to a parent user session. ([tool schema](https://github.com/juicesharp/rpiv-mono/blob/main/packages/rpiv-ask-user-question/docs/tool-schema.md)) |

**Parley verdict:** `rpiv-ask-user-question` is a capable questionnaire, but it is **not a cutover replacement** for Parley. The trade is simpler, native Pi/RPC dialogs for fewer question types and no explicit recommendation-acceptance, deferral, or durable round/session-forwarding semantics.

## Pick one

- **Question UI:** Keep Parley as the user’s structured decision/review surface. Do not add `rpiv-ask-user-question` as a second questionnaire provider unless you intentionally accept two competing question workflows. Gentle Pi also owns an `ask_user_question` tool, which conflicts by name.
- **Plan workflow:** Make `@narumitw/pi-plan-mode` authoritative for planning and approval. Use Plannotator’s review and annotation commands as a separate optional surface; do not activate both plan workflows for the same session. Plannotator’s browser review is a useful complement, but its own documentation says planning Bash is unrestricted.
- **Footer:** Pi’s default footer is the no-extension baseline. If retaining an information-rich OMP-style statusline, use **only `@narumitw/pi-statusline`**. Do not load `pi-powerline-footer` with it: both own the footer. Herdr already displays agent state; omit a duplicate activity segment. `pi-pretty` is not a footer owner, but it does take over tool rendering and the prompt editor/working indicators.
- **Todo:** Use `rpiv-todo` in standalone Pi. Skip it in a Gentle Pi-managed home, where Gentle provides its own Todo and removes the conflicting package.

## Gaps where we still need our own plugin

- **Keep Parley** for multi-round decision trees, explicit recommendations, notes/defer/pending semantics, reopenable rounds, and forwarding answers from user UI back into the correct session. `grilling` and `to-questionnaire` rely on this richer contract (`plugins/debate/common/skills/grilling/SKILL.md:39-56,75-110`; `plugins/debate/common/skills/to-questionnaire/SKILL.md:45-60`).
- **Keep `modes`** for the OMP-specific Debug, Refactor, and Concept boundaries. Pi Plan Mode supplies a plan workflow, not those agent-specific restrictions (`plugins/modes/opencode/src/modes.ts:9-30`).
- **Keep `debate`** for the two-sided decision analysis and the user’s grilling/questionnaire process; UI packages supply input controls, not those methods (`plugins/debate/common/skills/debate/SKILL.md:10-20,67-71`).
- **Keep existing OMP workflow guidance** for Beads, worktrunk, fan-out/merge-back, and PR proof. None of these packages is a drop-in replacement for those conventions.
