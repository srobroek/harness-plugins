# Engineering

This page records the stack, layout and standards for `srobroek/harness-plugins`. [AGENTS.md](../AGENTS.md) holds the agent rules and the command list. This page links to it instead of repeating it.

## Stack

The repository is a workspace of OpenCode V2 plugins written in TypeScript, and most plugins also ship a Claude Code tree. A server entry (`opencode/src/index.ts`) default-exports `Plugin.define({ id, setup })` from `@opencode/plugin`. A TUI entry (`opencode/src/tui.tsx`) uses the TUI API and has its own shape; `statusline` has only that entry. No plugin uses the V1 API (`@opencode-ai/plugin`).

The build leaves these modules external (`HOST_MODULES` in `scripts/build.ts`): `@opencode/plugin`, `effect`, `@opentui/*` and `solid-js`, with their subpaths. OpenCode supplies them at runtime. `@opencode/client` and `@opencode/theme` are not on that list. AGENTS.md has the pinning rule for the `@opentui/*` and `solid-js` host modules.

The TypeScript config extends the harness-kit base, which is strict and adds `noUncheckedIndexedAccess` and `moduleResolution: bundler`. The repository config adds `verbatimModuleSyntax`. Tests run under `bun test` with the preload `scripts/test-preload.ts` (see `bunfig.toml`).

## Layout

```
plugins/<name>/     one plugin per directory, a workspace package
lib/                @srobroek/opencode-lib, shared helpers, internal
shared/             agent bodies that several plugins ship
scripts/            build, generators and repository checks
tests/              tests that span plugins
docs/               design notes, decisions and this file
examples/           example projects included in typecheck
```

A plugin has `package.json`, `agents.src/` or `common/` (skills, agents, formulas), and one directory per harness: `opencode/` with `src/`, a committed `dist/` and one shim per entry declared in `agent-plugins.entries` (`index.js` for a server entry, `tui.js` for a TUI entry), and `claude/` where the plugin ships to Claude Code. AGENTS.md Generated files says which of these are sources.

## Dependency direction

Intended rules:

- Plugins import `lib` as `@srobroek/opencode-lib/<module>`. The build inlines `lib` into each plugin's bundle, because OpenCode installs a plugin from its own directory. So `lib` exists at build time only.
- Runtime `dependencies` of a bundle sit in the root `package.json` or in `lib/package.json`, because workspace packages do not exist at runtime.
- `lib` imports no plugin.
- `scripts/` and `tests/` may import from `lib/src` and from any plugin.
- Shared code goes into `lib`.

Current exceptions, found by searching relative imports under `plugins/*/opencode/src`: none in plugin source. Two edges run from scripts and tests into plugins:

- `scripts/agent-profiles.test.ts` imports `plugins/agent-efficiency/opencode/src/lean.ts`.
- `tests/agent-fallbacks.test.ts` and `tests/formulas.test.ts` import plugin source, for example `plugins/beads/opencode/src/subagent-routing.ts`. A test that spans plugins belongs in `tests/`.

Move new shared code into `lib` instead of adding another edge.

`lib/src/session-lanes.ts` holds the lane session helpers (`laneSessions`, `moveSessionsHome`, `isSessionNotFound`, `insideDirectory`) that `subagent-worktree` and `delivery` use. Both move a lane's sessions (its root and every session below it by parent ID) home after the worktree is removed, never by a project-wide listing:

- `subagent-worktree` removes a lane through one path, `finalize` in `plugins/subagent-worktree/opencode/src/lifecycle.ts`, under the worktree's disk lock. It records the lane as `removing`, re-proves liveness and the tree, removes the worktree, moves the sessions and retires the lane. A failed move or an incomplete listing leaves the lane in `removing` until a later trigger finishes it.
- `delivery` wraps the helpers in `plugins/delivery/opencode/src/lane-move.ts`. After it removes a worktree and proves it absent, it moves the lane's sessions that sit in the worktree or below it to the canonical checkout. A failed move, an unreadable session or an incomplete listing is reported in the cleanup result and never fails the cleanup; only a session the host says does not exist is dropped silently.

`subagent-worktree` runs git automatically in lanes and checkouts whose config it does not control. So `spawnRunner` in `plugins/subagent-worktree/opencode/src/git.ts` gives every `git` command `untrustedLocalGitArgs()` and the environment from `untrustedLocalGitEnv()`, both in `lib/src/safe-git.ts`. The environment drops every inherited `GIT_*` variable except `GIT_CONFIG_GLOBAL`. It also drops `PAGER`, `EDITOR`, `VISUAL` and `SSH_ASKPASS`. The dropped variables include these:

| Why | Variables |
| --- | --- |
| The filter-driver listing and the command could read different config | `GIT_CONFIG`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>`, `GIT_CONFIG_VALUE_<n>`, `GIT_CONFIG_SYSTEM` |
| They select another repository, work tree or index | `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES` |
| They name programs | `GIT_EXEC_PATH`, `GIT_EXTERNAL_DIFF`, `GIT_PAGER`, `GIT_EDITOR`, `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `GIT_PROXY_COMMAND` |
| They write files or change what a read sees | `GIT_TRACE*`, `GIT_*_PATHSPECS`, `GIT_NAMESPACE`, `GIT_REPLACE_REF_BASE` |

`GIT_CONFIG_GLOBAL`, `HOME` and `XDG_CONFIG_HOME` stay, because the listing and the command read the global config the same way. Together, the arguments and the environment disable these:

`GIT_CONFIG_GLOBAL`, `HOME` and `XDG_CONFIG_HOME` stay, because the listing and the command read the global config the same way. Together, the arguments and the environment disable these:

- fsmonitor, hooks and the global attributes file
- `diff.external`
- every transport
- `core.sshCommand`, `credential.helper` and `core.askPass`
- signature checks (`log.showSignature`) and the signature programs
- system config, terminal prompts and lazy fetch

Before a status or a work-tree diff, the plugin lists the filter drivers in the same directory (`FILTER_DRIVER_LISTING`). It disables every driver it finds, including the user's global ones such as git-lfs. The repository picks the driver, and it can supply the program that a relative command runs. It refuses to run the command when the listing fails or a driver name is not UTF-8 or contains `=`. The plugin reads `git worktree list --porcelain -z` and refuses malformed output. The minimum git version stays as it is, so these risks remain:

- `GIT_NO_LAZY_FETCH` needs git 2.45. Older git still starts a lazy fetch and relies on the transport refusal (`GIT_ALLOW_PROTOCOL` set empty).
- `git status` recursing into a submodule runs with the submodule's own filter drivers.
- A config change between the driver listing and the command is not seen. Git evaluates conditional includes (`includeIf`) the same way for both, because both run in the same directory.
- `wt` commands (`wt list`, `wt merge`) run without these settings.

With git-lfs disabled, an LFS file whose index entry is stale reads as modified. A lane then looks dirty and is kept, never removed.

`plugins/parley/opencode/src/guards.ts` holds the `isRecord` and `strings` type guards that the parley parsers share.

`plugins/parley/opencode/src/test-wait.ts` holds the state-driven test waits: `until` (polls an observable effect, fails after 2 s), `opened` (waits for a round to open) and `quiet` (a few event-loop turns, for "nothing happened yet" checks).

`plugins/autopilot` owns two kinds of state. Run state (`state.<N>.json` generations, `journal.jsonl`, `summary.md`) lives under `<git common dir>/opencode-scratch/autopilot/<run-id>/`. The armed-session index lives in plugin storage (`armed/<sessionID>`). On load, the plugin re-arms from storage. `/autopilot resume` re-binds a run to a new session from its latest state generation. Its tick is an OpenCode automation (a code action created through `tools.opencode.automation_create` that calls `autopilot_status`). An in-process timer covers hosts where that call fails. A run owns one beads ledger, resolved at arm (`resolveLedger` in `plugins/autopilot/opencode/src/ledger.ts`): the `ledger` setup field if given (a `.beads` directory or the checkout holding one), else the ledger the scope's bead id routes to, else the session directory's ledger (`sessionPinFor`, which ignores an inherited `BEADS_DIR`). Routing follows bd's `docs/multi-agent/routing.md`: a ledger's `.beads/redirect` is followed first (first non-comment line, relative to the directory holding the `.beads`, one level); only that resolved ledger's `routes.jsonl` is read, never a parent's; a route prefix must end in `-` (one without matches nothing); the longest prefix that the id starts with wins; `path` is relative to the directory holding the `.beads`, and a routed target's own redirect is followed. A path or route that is no ledger refuses the arm, and so does a `routes.jsonl` or `redirect` that is present but cannot be read safely (a symlink, a special file or over 64 KiB): absent means no routes, unreadable means routing cannot be checked. The ledger is stored in the run state (`ledger`, optional so earlier state files still decode; such a run derives its ledger from its scope and directory as arming would, and has none, so reads and writes refuse, when that fails) and every plugin `bd` call gets it as `BEADS_DIR` in the spawned process's environment, as does the write lock. A write that names a bead whose prefix routes to another ledger, or whose routes cannot be read, is refused. Its own `bd` writes take the embedded-store lock from `lib/src/bd-embedded-write-lock.ts`. Every run state transition holds the lease lock from `lib/src/lease-lock.ts` at `<run-id>/run.lock`, for liveness only. Lease releases check the owner token. State files are versioned and created exclusively: a write of generation N+1 writes its own temporary file and `link`s it to `state.<N+1>.json`, which fails with `EEXIST` when that generation exists. The losing writer journals an issue and the call returns `stale`; nothing is ever overwritten, and there is no write lock or age-based clearing. Readers take the highest generation and validate it with `effect/Schema` (the host's `effect`); a corrupt latest generation is a blocker, never skipped. After a successful link the writer prunes all but the latest five generations. `state.json` is a symlink to the latest generation for people reading the directory; the plugin never reads it. A stop passes through a `stopping` phase until `summary.md` and the handoff bead both exist. Ticks carry a binding token, so a resumed run's old automation goes stale. While a run is armed, its permission hook denies every `ask` and journals it as a blocker, with three exceptions that turn an `ask` into an allow and touch no other effect. An `external_directory` ask for exactly `<root>/*` is allowed when `<root>` is a writer lane's linked, non-primary worktree that `ctx.worktree.list` shows for the project, recorded at a tick with its real path, device and inode (the `worktrees` field of the run state), still a plain directory (`lstat`, not a symlink) with the same device, inode and real path, and free of `*` and `?`; both sides are compared by `realpath`. An `autopilot_merge` ask for `<pr>@<sha>` is allowed under `--allow merge`; the tool then requires a GitHub review `APPROVED` on that head by someone other than the PR author (comments never count), all check runs and statuses green plus every required context (unreadable branch protection or rulesets refuse, and so does a merge-queue ruleset), and a `method` the repository allows. It re-reads the PR's base and head just before merging and refuses on drift, then merges with `gh api -X PUT .../pulls/{n}/merge -f sha=... -f merge_method=...` as an argument array (never `gh pr merge`, so no auto-merge and no `--admin`). Success needs `merged: true` and a `sha`; any non-2xx response is a refusal journaled with its status and message. A final re-read must show a `MERGED` PR at the reviewed head with a merge commit. The third is an `external_directory` ask for `<dir>/*` where `<dir>` is the one export directory the run made last (`review/<head>/<manifest hash>/`, recorded in plugin storage as `review-current/<run-id>`) or a directory under it (`reviewExportAsk`; real paths compared, the directory an `lstat`-plain directory, no `*` or `?`, so a symlink out, a `..` climb, a sibling, `review/` and an older export fail). The host's types (`PermissionEvaluation`: action, resources, metadata, tool call id) give the resource only as an opaque string and carry no read/write distinction, so the grant is on the directory and a session whose rules allow `edit` can write there: the allowed path is model-writable. Integrity comes from the export's manifest, not from the permission. `autopilot_export_review({ pr, base, head })` (`review-export.ts`) runs git as argument arrays in the run's repository with `--no-ext-diff` and `--no-textconv`, rejects revisions that are not strings, start with `-` or hold whitespace, resolves both with `git rev-parse --verify <rev>^{commit}`, and publishes `<run dir>/review/<head-sha>/<manifest-hash>/{manifest.json,round.diff,diffstat.txt,files/<path>}` through a temporary directory. `manifest.json` holds the SHA-256 and size of the diff, the diffstat and every file; its own hash is returned and stored in plugin storage under `review/<pr>@<head>`. Exports are immutable: nothing published is deleted or overwritten, and re-exporting identical content returns the existing directory when `verifyExport(dir, storedHash)` accepts it, otherwise renames the damaged one to `.rejected-<id>` and publishes a fresh one. `verifyExport` refuses a hash mismatch, a changed, extra or missing file or directory, and any symlink or non-regular file. `round.diff` is the three-dot diff `base...head`. Caps (300 files, 4 MiB diff, 512 KiB per file, 8 MiB of content) refuse the export before anything is written, except the per-file cap, which skips and lists the file. Lead-spawned export reviews go to `code-reviewer` (its permissions: `read`, `grep`, `glob` allowed, `external_directory` ask, everything else denied); `pr-reviewer` keeps its contract and gets no export paths. `autopilot_review({ pr, sha })` (`review-session.ts` for the pure parts, the `Autopilot` class for the host calls) lets a merge rest on a verdict the model cannot forge, under the `self-review` grant (default off). It first takes the once-only claim (below), then reads the PR from GitHub (`gh api repos/{owner}/{repo}/pulls/<n>`: `state` is `open`, `head.sha` is `sha`, plus `base.sha` and `changed_files`), refuses when the `code-reviewer` agent (`ctx.agent.get`) is missing, fetches `base.sha` with `git fetch --no-tags origin <sha>` (a failed fetch is tolerated, a missing commit is not), runs `exportReview` against that base SHA and never a branch name, refuses an empty diff or a changed-file count that differs from GitHub's (below), and records the manifest hash as above, then `verifyExport`s against the stored hash, reads `round.diff` through `readBoundedBytes` (cap 256 KiB; the bytes must hash to the manifest's diff entry) and builds the prompt: the diff between lines carrying a random delimiter and labelled untrusted, ending with the exact lines `VERDICT: APPROVE <sha>` and `VERDICT: REQUEST_CHANGES <sha>`. It creates the reviewer with `ctx.session.create({ parentID: lead, agent: "code-reviewer", location, metadata: { source, pr, sha, nonce }, permissions })` (permissions deny `edit`, `shell`, `subagent`, `autopilot_*`), stores a pointer under `review-session/<lead>/<pr>@<sha>` (`pr`, `sha`, `session`, `nonce`, `promptHash`, `manifestHash`, `at`), verifies the export again and sends the prompt with `ctx.session.prompt`; a failure after the create removes the pointer and the session. The call returns at once and does not use `session.wait`. A verdict is never stored: `autopilot_status` (field `reviews`, which also drives the deadline) and `autopilot_merge` derive it with `resolveReview` from `ctx.session.get` and `ctx.session.context` of the child. It requires the child's id, parent (the lead), agent and metadata to match the pointer; exactly one `user` message whose SHA-256 is `promptHash`; no `synthetic` message and no switch to another agent; the last `idle` message and the session `outcome` both `succeeded`, with no user or assistant message after that idle; and the final assistant message (`finish: "stop"`, no error) whose `text` parts, read by `parseVerdictLine` in `lib/src/review-verdict.ts` outside any code fence, end in a `VERDICT:` line whose remainder is exactly `sha`. The verdict line must be the last non-blank line of that text (`parseVerdictLine` with `strict`), so an approval followed by a retraction is none. The turn's finish time from the transcript (the idle message, and the assistant message's `time.completed` when present) must be within 30 minutes of `at`, else the review is void however soon it is polled. Anything else is `void` with a reason. A reviewer without an idle 30 minutes after `at` is interrupted and voided; `autopilot_status` sweeps the lead's pointers with a rotating cursor (below) and shows the newest 20. **Once-only claim:** before any reviewer exists, `autopilot_review` creates two claim files in `<git common dir>/opencode-scratch/autopilot/review-claims/`, beside the run directories so they outlive a run: `pr-<pr>@<sha>` and `head-<sha>` (a head is reviewed once whatever PR number names it). Each is written to a temporary file and hard-linked to its name, so `link` fails with `EEXIST` when it is taken, as for run state generations; a collision releases the claims taken before it and refuses. A claim is released only when the start is refused and no reviewer is left behind, never after a verdict, void, deletion, interrupt or follow-up. A cleanup that fails (pointer or session removal) is journaled as an issue and keeps the claim. The claim files sit in the same scratch area as the run state, so the same-user residual risk below covers them; plugin storage is the second line: before starting, the call scans every `review-session/` key and refuses when any ends in `@<sha>` (any lead, any PR number, any outcome), and a storage read that fails (here, on the pointer read in a merge or a repeated call, on the sweep, on the manifest hash and on the current-export read) refuses the operation, is journaled once as a `blocker` and is listed in `autopilot_status` as `storageErrors`, labelled by operation and resource (`get:<key>`, `scan:<prefix>`, `set:<key>`, `remove:<key>`); a label clears only when that same operation on that same resource succeeds, and a scan label only when that scan completes to the end (a lead-local scan never clears a failed global one). A failure is never taken as no record or as the end of a scan. A sweep cursor that cannot be read stops the sweep (no start-of-list default, no cursor write), and a merge under the `self-review` grant refuses outright when the review record is unreadable, before the GitHub approval is looked at. Pointers are deleted only by a refused start. The export is refused when the recorded diff is empty, and when the number of files in `git diff --name-status -M -z base...head` (a rename counts once, as GitHub's `changed_files` counts it; a deletion-only PR passes) differs from the `changed_files` of `pulls/<n>`. Status resolves the newest 20 pointers and the next 25 after the cursor in `review-sweep/<lead>` (plugin storage, wrapping at the end), so every pointer meets its deadline over successive calls with no cap on how many exist. The run state, the journal and `autopilot_log` are never read for a verdict, and the pointer is only a locator that the transcript must confirm. In `mergeRefusal` the `witnessed` input (`{ granted, approvedSha }`) replaces only the `reviewApproval` check, and only when the grant is set and `approvedSha` is the head being merged; checks, required contexts, the merge-queue and method checks and the head and base drift re-reads still run. Residual risks: prompt injection through the diff can talk the reviewer into `APPROVE` (the fence-aware parse stops a forged verdict line, not a persuaded reviewer); same-user writes to the scratch area, to the host database (`~/.local/share/opencode/opencode.db`) and to the server API are out of scope (they can create or edit sessions and forge a record the plugin accepts); `--allow self-review` is weaker than a second GitHub account; GitHub branch protection that requires approving reviews still refuses the merge. The decisions are pure functions in `plugins/autopilot/opencode/src/policy.ts`. The approval and check judgments are in `lib/src/pr-approval.ts`, which `delivery` also uses; `delivery` keeps its comment-verdict support behind that module's `commentVerdict` option, and autopilot runs the strict mode (review-only approval, `requireKnown` required contexts, `requireBoth` protection and rulesets).

## safety permission relaxations

`plugins/safety` turns some `external_directory` asks into allows in `permission.hook("evaluate")` hooks that run before `denyUnanswerable`, because a subagent cannot answer a prompt. Each hook acts only on an `ask`, never overrides a deny, and has a pure decision function tested directly (`scratch-dirs.ts`, `skill-references.ts`, `steering-dirs.ts`, `repo-worktrees.ts`). A hook can be switched off through the plugin's `disable` list:

- `scratch-dirs.ts`: the OpenCode temp folder and the project's worktree folder, for direct file tools and (`scratch-shell`) the `shell` tool. For shell it only waives the `external_directory` ask when every parsed resource lies inside a pinned root; it does not confine the process, which can still read or write elsewhere as any allowed shell can. An empty resource list is never auto-approved.
- `skill-references.ts` (`skill-references`): read-only tools inside listed skills' directories.
- `steering-dirs.ts` (`steering-dirs`): read-only tools inside the `steeringDirs` option, default `~/.config/opencode/steering`, realpath-resolved, user-owned.
- `repo-worktrees.ts` (`repo-worktrees`): read-only tools inside the worktrees of the session's repository. `git worktree list --porcelain -z` runs through `lib/src/safe-git.ts` flags and `lib/src/subprocess.ts` supervision with repository-selecting `GIT_*` variables cleared. Each path must link back reciprocally on disk (`.git` file and `<common-dir>/worktrees/<name>/gitdir`) and be user-owned. Roots are cached 30 s per directory with device and inode and re-checked on every use.
- Roots are compared as canonical paths (`insideCanonical`), never re-resolved after the check.
- `subagent-external-reads` (below) already allows any non-secret read or shell ask in a subagent session. The relaxations above stay narrower and also apply to root sessions; with `subagent-external-reads` disabled they are what lets a subagent read these places.

## Standards

[AGENTS.md](../AGENTS.md) Conventions covers bundles, generated files, vendored `plugins/cad` files, agents, skills, pitfalls and descriptions. Checks enforce most of it. This page adds:

- Renovate (`renovate.json`) extends the `srobroek/harness-kit` preset and adds six regex custom managers. Two read exact PyPI and npm pins in Markdown sources: `uv run --with PKG==VER`, `uvx PKG@VER`, `npx [-y] PKG@X.Y.Z` and `npm:PKG@X.Y.Z`. Two read the same pins in `plugins/<name>/common/.mcp.json`. One reads `REPOMIX_VERSION` in `plugins/repomix/opencode/src/pack.ts`. One reads the exact analyzer pins in `plugins/code-challenge/opencode/src/scan/pins.ts` (see Code-challenge scan below); each pin sits on the line after a `// renovate: datasource=<npm|pypi|go> depName=<package>` annotation, and a test keeps the manager's regex and the file in step. The Markdown managers select source files only: `docs/` and `lib/`, plugin READMEs, `common/` and `agents.src/`, and `opencode/src/` Markdown. Copies that `harness-kit build` writes are not selected. A package rule disables these managers for the vendored `plugins/cad/common` and `plugins/cad/opencode`. Version pins in skills and docs use the shapes these managers match.
- The preset also moves `@srobroek/harness-kit` (package pin), the `srobroek/harness-kit` workflow tags and the versions quoted in any Markdown file (`srobroek/harness-kit/.github/workflows/<file>.yml@vX.Y.Z`, `@srobroek/harness-kit@X.Y.Z`) in one `harness-kit` group. `.github/workflows/renovate-regenerate.yml` runs `bun run build` on same-repository Renovate PRs to regenerate the copies.
- Approved departures:
  - `code-challenge` names its tool `challenge_setup`, not `code_challenge_setup` as `<name>_<verb>` would give. The skill's other two tools, `challenge_lib_facts` and `challenge_scan`, share the same `challenge_` namespace, so one short prefix (reserved in `RESERVED_TOOL_PREFIXES`) covers the family and the agents' permission rules.
  - `code-challenge` `challenge_scan` runs analyzers without a sandbox, by user decision. It discloses the risk and asks for consent instead (see Code-challenge scan below).

## Read-only shell rules and subagent reads

- `lib/src/read-only-shell.ts` owns `READ_ONLY_SHELL_RULES`, the one shell permission list of every read-only agent: `shell "*"` allowed, then a deny list for repository, remote, ledger and file mutations, `git -c`/`--config-env`, and visible redirection (`*>*`, `| tee`). Agent sources put `# {{rules read-only-shell}}` inside `permissions:`; `composeAgent` (`lib/src/fragments.ts`) expands it. `plugins/cad` gets it through the `readOnlyShell` overlay in `scripts/sync-cad.ts`, and `explore` (`plugins/agent-efficiency`) spreads the list. `tests/read-only-shell.test.ts` keeps every shipped read-only agent in step with it. `pr-reviewer` is not on this list: it reads untrusted PR content and stays on a two-command `gh pr` allowlist.
- Enforcement limit: this is best-effort, the owner's chosen trade-off, not a sandbox. It stops accidental writes by a read-only agent, not a determined one. Prefix and pattern matching can be bypassed by interpreters (`python -c`, `node -e`), nested shells (`bash -c`), `git -C x push` and forms the matcher does not see. Those stay out of scope; do not grow the list into a parser.
- `plugins/safety/opencode/src/subagent-reads.ts` owns the `subagent-external-reads` hook (feature id of the same name, registered before `subagent-prompts`). In a subagent session it turns an `external_directory` ask into an allow for `read`, `glob`, `grep`, `list` and the shell. Edit, write and patch keep the ask. Secrets keep it too: `SECRET_LOCATIONS` (exported), `*.env` and `*.env.*`, plus the `subagentSecretPaths` option. Limits: paths resolve through `realpath` before any check; a resource that is inside or an ancestor of a protected location (`~/*`, `/*`) is refused; a relative path, a mid-path wildcard or `..` keeps the ask. A root session is unchanged. `disable: ["subagent-external-reads"]` turns it off.
- `scratch-dirs.ts` also allows the session directory spelled through a symlink alias, `<data>/opencode/shell/<project id>` and `<data>/opencode/tool-output`.

## code-challenge

`plugins/code-challenge` is OpenCode only (`harnesses: ["opencode"]`). It challenges existing code for simplification, performance, stability, hand-rolled code and structure, and plans only: it edits no source file.

- Ownership: the plugin owns the `code-challenge` skill (twelve lens references, the report and decisions JSON Schemas, intake, scoring and run-storage rules), the `/code-challenge` command, the `challenge_setup`, `challenge_lib_facts`, `challenge_validate` and `challenge_scan` tools, nine beads formulas and the `code-challenger` and `refactor-challenger` agents. `challenge_scan` is documented under Code-challenge scan.
- Run storage: every run writes under `<git-dir>/code-challenge/<run-id>/`, outside the working tree (`intake.json`, `scan.json`, `findings.json`, `research.json`, `verdicts.json`, `decisions.jsonl`, `report.json`, `report.md`). `decisions.jsonl` is append-only. The directory is never committed.
- Formulas: `challenge_setup` copies `code-challenge` (the full run), `mol-challenge-<phase>` for the seven phases and `mol-challenge-lens` into `.beads/formulas/`. The lead agent sequences the phases, dispatches subagents and writes every file, bead and log line. Only `mol-challenge-lens/analyse-lens` (to `code-challenger`) and `mol-challenge-refute/attack-findings` (to `refactor-challenger`) route to a subagent. Both agents are read-only; each routed step lists `requires_actions` and a test checks the agent's permissions allow them.
- `challenge_setup` resolves the target workspace from the invoking session's directory and fails when it cannot read that session.

### code-challenge `read-grant.ts`

`plugins/code-challenge/opencode/src/read-grant.ts` (`referenceReadRules`) lets both challengers read the skill's reference files without a prompt, because an installed plugin's skill sits outside the project and a subagent cannot answer an `external_directory` ask.

- Scope: exactly `<skills root>/code-challenge/references/*`, as an `external_directory` allow. `SKILL.md`, the skill's parent, other skills and the project are not covered.
- Fail closed: the grant is made only when `realpath(references)` equals `realpath(skills root)/code-challenge/references`. A symlink to the parent or outside, any other mismatch, or a missing directory means no grant and one warning.
- The rules are built once at setup from the two validated paths with `directoryReadRulesFor` (`lib/src/agent-files.ts`), which never touches the file system, so no second resolution can add a pattern. `directoryReadRules`, which resolves the path itself, stays for `cad`.
- Trust assumption: the check is a single point in time at setup. A later swap of `references` is bounded by the validated pattern, but the host follows symlinks when it reads, and that is outside this plugin's control; the install directory is assumed writable only by the installing user.

### code-challenge `challenge_validate`

`plugins/code-challenge/opencode/src/validate.ts` registers `challenge_validate`. It takes the absolute run directory, reads only `report.json` and `decisions.jsonl`, and checks them against the shipped schemas with `opencode/src/json-schema.ts`, the small in-repo validator that already guards the schemas in tests (it throws on a keyword it does not know). No JSON Schema library is added.

### code-challenge `challenge_lib_facts`

`plugins/code-challenge/opencode/src/lib-facts/` registers the `challenge_lib_facts` tool (`registerLibFacts(ctx)`). It returns facts about 1 to 6 packages (npm, PyPI, crates.io, Go) and no verdicts, and uses `fetch` with no HTTP library.

- External sources, all HTTPS: `api.deps.dev` (v3, and v3alpha for dependents), `registry.npmjs.org`, `api.npmjs.org`, `pypi.org`, `pypistats.org`, `crates.io`, `proxy.golang.org`, `api.osv.dev` (`querybatch`) and `api.github.com`. Each source can fail alone; the failure is listed in the package's `missing`.
- OSV is never cached. An OSV reply with a wrong result count, a continuation token or a malformed vulnerability list is a failure, so the CVE gate reads `null` instead of passing.
- GitHub token boundary: the tool runs `gh auth token` itself (5 s timeout) and sends the token only as the `Authorization` header of requests to `api.github.com`. It is never logged, returned or cached. Redirects are followed by hand and only within the original host. Repository URLs come from publisher metadata, so only recognised github.com forms are used, `owner` and `repo` must match GitHub's charset, and each part is `encodeURIComponent`-ed into the path.
- Input limits: package names are checked per ecosystem (no `?`, `#`, `..`, control characters or backslashes; at most 214 characters) and versions must be plain version strings.
- Cache: one JSON file per request under `$XDG_CACHE_HOME/opencode/code-challenge/lib-facts` (`~/.cache/...` by default), 7-day TTL. GitHub replies are reduced to the public figures the tool reports before they are stored, and a cached value of any other shape is a miss. File names carry a schema version (`v2-`); files of any other version are never read and the sweep deletes them. A file over 256 KiB (measured in UTF-8 bytes) is neither written nor read, and an entry that fails its shape check is deleted. An expired entry is deleted on read, and the first write of each call sweeps expired files and trims the directory to 2000 entries.
- Request limits: 6 requests in flight, a 10 s timeout each, 5 MiB per reply (checked while streaming, before `JSON.parse`) and 3 same-host redirects.
- Licence gate: `ALLOWED_LICENCES` in `licence.ts` lists permissive and weak-copyleft SPDX ids. `spdx-expression-parse` evaluates expressions with grouping, `AND` and `OR`; it is a small, widely used parser (the one `npm` tooling uses) and replaces a hand-written grammar that mishandled parentheses. It is inlined into the bundle like `jsonc-parser`.

## Code-challenge scan

`plugins/code-challenge/opencode/src/scan/` is the `challenge_scan` tool module of the SCAN phase. `registerScanTool(ctx)` in `scan/index.ts` registers the tool and a permission hook, and returns one dispose function. The module adds no runtime dependency.

- `recipes.ts` is the recipe table: for each existing analyzer, its language, lenses, arguments, accepted exit codes, parser, whether it needs a build (quick depth skips those), how it is installed and whether it runs repository code. It uses no custom rules. `parsers.ts` turns each tool's output into hits; output that is not in the tool's format is a coverage gap, never "no findings".
- `run.ts` plans (language, lens, depth, repository markers, tool resolution, consent), then executes each recipe and returns candidates, coverage (`ran`, `skipped`, `gap`) and per-tool timings. `probes.ts` computes `ruleEnabledInRepo` for ruff (one `--show-settings` per config) and golangci-lint; every other tool reports null.
- Each lens profile ignores the repository's rule selection (`--isolated`, `--no-config`, a temporary config, or `-A clippy::all`) but keeps `.gitignore` and inline suppressions. Biome ignores `--config-path` when the root has a `biome.json`, so then it runs from its own config directory on an explicit list of files that git does not ignore.

### Provisioning and pins

- Nothing installs globally. A recipe uses the binary on `PATH`, else a one-off `bunx -p`, `uvx --from` or `go run` of an exact pinned version from `scan/pins.ts`. A missing tool is a coverage gap.
- `eslint` and `@e18e/eslint-plugin` must sit side by side, because the plugin resolves from the config file. The scan never installs them: it reports the pinned `bun add` command and looks in `<git-dir>/code-challenge/tools`, where it also writes the eslint config.
- Renovate moves the pins through the manager for `pins.ts`. Bump a pin together with a run of the recipe's command, because a flag can change between versions.

### Trust and consent

- There is no sandbox, by user decision. The scan discloses what it runs and asks for consent, per canonical root, before it runs anything that is not static analysis: clippy (build scripts and proc macros, writes `target/`), golangci-lint and deadcode (compile Go, may fetch modules), knip and import-linter (load repository config code), and every one-off `bunx`, `uvx` or `go run`. Without consent those recipes are coverage gaps with the reason; recipes that run no repository code still run.
- Consent is an approved set, not a flag. The tool computes the risky recipes (`consentRisks`), asks once through `permission.assert` with the resource `<canonical root> [<sorted recipe ids>]` (so a saved approval covers exactly that set), and passes `ScanDeps.approved` (a set of recipe ids) to `runScan`. A risky recipe outside the set is a gap, "not approved for this run"; a plan with no risky recipe approves nothing and asks nothing. `approved` is host-side only; tool input cannot set it. `confirmScan` turns an allowed scan with risky recipes into a prompt that lists them.
- Every rejection of the prompt (deny rule, feedback, interruption) propagates as the host defines it, as in `dep-update` and `safety`. The voluntary way to scan without the risky recipes is the `staticOnly` input, which asks nothing.
- Analyzer processes get an allowlisted environment (`env.ts`): `PATH`, `HOME`, `TMPDIR`, locale, toolchain and cache variables, proxy and CA variables. Variables whose names look like credentials, and `AWS_*`, `GH_*` and `GITHUB_*`, are dropped, even under an allowed prefix such as `UV_`.
- File names reach tools as absolute paths after `--`. Every named path and glob is resolved with `realpath` and must stay inside the canonical root. Symlinks met while walking or globbing are skipped. A run id is one path segment (`^\w[\w.-]{0,63}$`).
- Output directories are created one real directory at a time, files are written with `O_NOFOLLOW`, and a symlink in the way is refused.
- Captured stdout (16 MiB) and stderr (1 MiB) are capped and an overflow ends the tool's process group; report files and marker files are `lstat`ed and size-capped; the per-tool timeout is capped at 900 s.
- Accepted residual risk: races on parent path components that need concurrent local filesystem control (swapping a directory for a symlink between the check and the use) are not defended. The model is a trusted local repository with no sandbox, by user decision.
- Tests: the Biome behaviour suite always runs (biome is a devDependency, resolved from `node_modules/.bin`). The ruff and golangci-lint suites in `scan/behavior.test.ts` skip with a printed reason when the binary is absent, and no workflow installs them, so CI skips them; they run on a machine that has them.

## Commands

AGENTS.md Commands lists every script. The `justfile` has one recipe per script, and `just verify` runs every gate CI runs ([decision 0006](decisions/0006-bun-and-just.md)): installs use `bun install --frozen-lockfile` and the lockfile is `bun.lock`, never npm. `bun run check` is `harness-kit check`: `build --check` for the generated files, then validation of each Claude Code tree. It does not run typecheck, lint, tests or the content checks. The `cad:*` scripts need network.

## CI

`.github/workflows/ci.yml` runs on pushes to `main`, pull requests and `workflow_dispatch`:

- `check` calls the reusable harness-kit workflow, pinned to the same tag as the package. It runs `bun install --frozen-lockfile`, `harness-kit check`, `bun test` and `tsc`.
- `repo-checks` runs `bun install --frozen-lockfile`, then lint, `build:check`, `plugin-table:check`, `steering`, `pitfalls`, `agent-roles`, `descriptions`, `concerns`, `scripts/check-release-prepare.ts` (in a temporary checkout, makes the delivery and cad bundles stale, runs each release prepare step and fails if a bundle is still stale), `scripts/check-test-executables.ts` and the Python unit tests of the shipped scripts.
- `cad` runs `cad:check` when `plugins/cad`, `scripts/sync-cad.ts` or the workflow changes.

`renovate-regenerate.yml` accepts only `opened` and `synchronize` events from `renovate[bot]`, for that bot's same-repository PRs on `renovate/` branches. Both job guards reject forks. It skips heads whose commit subject is `chore(deps): regenerate generated copies`.

The build job has only `contents: read`. It checks out the event's head SHA without persisted credentials, runs install/build/check and uploads a generated-file patch. SHA-pinned first-party upload/download actions transfer that patch within the same workflow run. The push job uses a separate runner with `contents: write`, `pull-requests: read` and `actions: write`. It runs no npm command or repository code, and checkout persists no credentials.

Both jobs validate the patch against the workflow's generated-path allowlist. It covers inventories, manifests, harness copies, bundles, runtime copies, shims, Claude hook output and composed/translated agents. Composed agents require a matching `agents.src/` file. Translations require an existing OpenCode form. Source changes, vendored cad common files and cad examples fail validation. The validator accepts UTF-8 text only and rejects binary data, symlinks and special file modes. Executable harness copies must match their `common/` source's mode. This preserves the shipped preflight scripts; bundles cannot acquire execute bits. The push job checks paths and modes in a temporary Git index before applying the patch to its checkout.

`renovate.json` ignores that bot's exact author email through `gitIgnoredAuthors`. Renovate can then rebase or update branches containing regeneration commits.

The push job commits as `github-actions[bot]` with Git hooks disabled. Branch names pass through quoted environment variables, not shell-source interpolation. If the remote head has moved, the job leaves regeneration to the next run. Git's fast-forward check prevents overwriting a concurrent push. After pushing with `GITHUB_TOKEN`, the job dispatches `ci.yml` on the PR branch. The final head receives the existing CI checks, including the vendored cad check. This uses GitHub's [documented dispatch exception](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-when-your-workflow-runs/triggering-a-workflow) to token-triggered workflow suppression. It needs no App token or PAT.

`.github/workflows/release.yml` runs on pushes to `main`. It calls the harness-kit release workflow, which runs multi-semantic-release (`release.config.mjs`, `.multi-releaserc`) and tags each plugin `<name>--v<version>`. The `prepareCmd` from `scripts/release-preset.mjs` (used by `release.config.mjs` and `plugins/cad/release.config.mjs`) runs `scripts/build.ts <name>` after `harness-kit stamp`, because a bundle can embed its plugin's `package.json` (delivery's receipts carry the version) and the release commit must carry the rebuilt `opencode/dist`. A `feat` or `fix` commit, and with the repository rules a `refactor` or `docs` commit, under `plugins/<name>/` cuts a release. A new plugin needs no manifest entry: any directory under `plugins/` is a workspace package.
