# Engineering

This page records the stack, layout and standards for `srobroek/harness-plugins`. [AGENTS.md](../AGENTS.md) holds the agent rules and the command list. This page links to it instead of repeating it.

## Stack

The repository is a workspace of OpenCode V2 plugins written in TypeScript; most also ship a Claude Code tree, and some ship pi extensions. An OpenCode server entry (`opencode/src/index.ts`) default-exports `Plugin.define({ id, setup })` from `@opencode/plugin`. A TUI entry (`opencode/src/tui.tsx`) uses the TUI API and has its own shape; `statusline` has only that entry. No plugin uses the V1 API (`@opencode-ai/plugin`).

### pi extension bundles

`agent-plugins.piEntries` maps names to TypeScript sources in `plugins/<name>/pi-src/`. The build writes each bundle to `plugins/<name>/pi/extensions/<name>.js`. Pi's package manifest lists only these generated extensions.

OMP loads Pi extensions unchanged. When a plugin lists the `omp` harness, the build also copies each bundle to `plugins/<name>/omp/extensions/<name>.js`. harness-kit lists that directory under `omp.extensions` in the generated `omp/package.json`. A bundle that imports a Pi host module at runtime must also work in OMP; `plugins/code-challenge/pi-src/` imports only types.

Pi's compiled runtime accepts Bun-targeted extension bundles. Pi resolves its host modules from its own copies:
`@earendil-works/pi-coding-agent`, `@earendil-works/pi-agent-core`, `@earendil-works/pi-ai`, `@earendil-works/pi-tui`, and `typebox`, including subpaths.
The builder inlines private `@srobroek/opencode-lib/*` imports.

The TypeScript config extends the harness-kit base, which is strict and adds `noUncheckedIndexedAccess` and `moduleResolution: bundler`. The repository config adds `verbatimModuleSyntax`. Tests run under `bun test` with the preload `scripts/test-preload.ts` (see `bunfig.toml`).

## Layout

```
plugins/<name>/     one plugin per directory, a workspace package
lib/                @srobroek/opencode-lib, shared helpers, internal
shared/             agent bodies that several plugins ship
scripts/            build, generators and repository checks
tests/              tests that span plugins
docs/               design notes, decisions and this file
examples/           example projects included in typecheck
```

A plugin has `package.json`, `agents.src/` or `common/` (skills, agents, formulas), and one directory per harness: `opencode/` with `src/`, a committed `dist/` and one shim per entry declared in `agent-plugins.entries` (`index.js` for a server entry, `tui.js` for a TUI entry), and `claude/` where the plugin ships to Claude Code. AGENTS.md Generated files says which of these are sources.

The `beads` PR bead gate does not port upstream's shell decoding (ANSI-C words, `env -S`, wrapper directories). `plugins/beads/opencode/src/pr-create-form.ts` accepts only literal `gh pr create`/`gh pr new` forms: a single command, `--body` or a relative regular `--body-file`, and a `Bead:`, `Closes-Bead:` or `Bead-Id:` line. Any other form that may reach `gh pr create` is refused in a gated repository, with the accepted form shown. A `gh api` call that may create a PR is such a form: a POST (`-X POST`, or any `-f`, `-F`, `--field`, `--raw-field` or `--input` without `-X`) to `repos/<owner>/<repo>/pulls` (relative, or an absolute `https://` URL such as `api.github.com`, `<ghes>/api/v3` or `api.<tenant>.ghe.com`), or one whose method or endpoint the gate cannot read. Flags parse as pflag does (`-X=POST`, `-i=false`). A GET (no field flag, or `-X GET`) passes. The control lookup for such a call uses the repository and host the endpoint names (`--hostname`, `GH_HOST` or the URL), not `GH_REPO`; The lookup name always carries the host (`github.com/o/r`), so an inherited `GH_HOST` never redirects it. `{owner}/{repo}` placeholders take only the owner and name from `GH_REPO` and keep the endpoint's host; a `GH_REPO` on another host fails closed. With no `GH_REPO` they resolve through the checkout, on github.com only. A destination it cannot resolve fails closed. When the command names no `--repo`/`-R`, the repository for the control lookup is `GH_REPO` from the session environment (`--repo` wins, as in `gh`; empty counts as unset), else the checkout. A `GH_REPO` that is not a repository name fails closed.

The gate judges the text of every heredoc and here-string, whichever command receives it, because `cat <<EOF | sh`, `tee >(sh) <<EOF` and a git shell alias all run it. Text that may create a PR as shell, names `gh`, has `pr` before `create` or `new`, holds a command word the gate cannot read, or is an expanding here-string is refused. Tradeoff: in a gated repository a commit-message heredoc that mentions `gh pr create` is refused too. Write the message without those words, or pass it with `-m`.

The gate catches an agent that forgets the bead or writes a form it cannot read. It is not a boundary against deliberate evasion: a script written in one call and run in a later one, `eval` of a built string, an alias, and a command built from variables all get past it. Only a server-side required check can give a hard guarantee.

## Dependency direction

Intended rules:

- Plugins import `lib` as `@srobroek/opencode-lib/<module>`. The build inlines `lib` into each plugin's bundle, because OpenCode installs a plugin from its own directory. So `lib` exists at build time only.
- Runtime `dependencies` of a bundle sit in the root `package.json` or in `lib/package.json`, because workspace packages do not exist at runtime.
- `lib` imports no plugin.
- `scripts/` and `tests/` may import from `lib/src` and from any plugin.
- Shared code goes into `lib`.

Current exceptions, found by searching relative imports under `plugins/*/opencode/src`: none in plugin source. Two edges run from scripts and tests into plugins:

- `scripts/agent-profiles.test.ts` imports `plugins/agent-efficiency/opencode/src/lean.ts`.
- `tests/agent-fallbacks.test.ts` and `tests/formulas.test.ts` import plugin source, for example `plugins/beads/opencode/src/subagent-routing.ts`. A test that spans plugins belongs in `tests/`.

Move new shared code into `lib` instead of adding another edge.

`lib/src/session-lanes.ts` holds the lane session helpers (`laneSessions`, `moveSessionsHome`, `isSessionNotFound`, `insideDirectory`) that `subagent-worktree` and `delivery` use. Both move a lane's sessions (its root and every session below it by parent ID that sits in the worktree) home after the worktree is removed, never by a project-wide listing:

- `subagent-worktree` removes a lane through one path, `finalize` in `plugins/subagent-worktree/opencode/src/lifecycle.ts`, under the worktree's disk lock. It records the lane as `removing`, re-proves liveness and the tree, removes the worktree, moves the sessions and retires the lane. A failed move or an incomplete listing leaves the lane in `removing` until a later trigger finishes it. Every plugin start also finishes the lanes it finds in `removing`. A `session.execution.failed` with `Location not found` for a lane's child or a session below it moves the lane's sessions home through the same path, but only when the lane's worktree is gone from disk. The plugin runs no background sweep and no project-wide session repair. `subagent_worktree_sweep` runs on demand.
- `delivery` wraps the helpers in `plugins/delivery/opencode/src/lane-move.ts`. After it removes a worktree and proves it absent, it moves the lane's sessions that sit in the worktree or below it to the canonical checkout. A failed move, an unreadable session or an incomplete listing is reported in the cleanup result and never fails the cleanup; only a session the host says does not exist is dropped silently.

`subagent-worktree` refuses a second writer in a named worktree. The guard is `decideWriterGuard` in `plugins/subagent-worktree/opencode/src/lane.ts`, and its comment lists the guard's three limits. A writer whose server died during a run keeps `time.busy` after `time.idle`. It blocks the worktree and keeps its lane. The guard does not see a deleted session. After the user deletes the writer's session, its parent can hand the lane to the next writer with `subagent_worktree_merge` method `release`:

- The rules are pure functions in `plugins/subagent-worktree/opencode/src/release.ts`. `index.ts` collects the facts under the worktree's disk lock (`lifecycle.spawnInto`).
- A release rests on one piece of host evidence: `session.get` reports the writer as not found (`deleted`). An idle, archived or running session is refused, because a run, shell or background job of it may still write and the plugin API lists no shells or jobs. What deletion stops, from the OpenCode source (anomalyco/opencode `ee5fe34e`, `packages/core/src`): `Session.remove` interrupts the session's run and waits for it to go idle (`session.ts:406-407`), cancels its running jobs (`session.ts:408`; `job.ts:212-219`, `596-600`), and removes its child sessions the same way (`session.ts:410`). A shell tool's job carries the session's id (`tool/plugin/shell.ts:218`), and cancelling it stops the command with SIGTERM, then SIGKILL after 3 s (`tool/plugin/shell.ts:248`; `shell.ts:433-448`). Deletion does not reach a PTY (`pty.ts` has no session link), a process that detached from its command, or a run in another server instance (`session/execution.ts:30`: "work owned by this process"). So the refusal and the README tell the user to close the writer's terminals and stop it before deleting it.
- A release also needs these: the writer's lane names the caller as its parent, `holdsState` finds no hold on the worktree, the worktree is clean, and its upstream has every commit.
- The release reads its record again under the lock, so it refuses a second release queued behind the first.
- The record goes under `release/<child>` in plugin storage. The plugin refuses every later resume of that child, and the next writer spawned into the worktree may take the lane over. The record's `to` names that writer for the audit trail only; no code path reads it to decide anything.
- The handover (`handOver` in `index.ts`) is one write of the same lane record. A lane keeps the storage key of the child it was made for (`Lane.id`, `laneStoreKey` in `lane.ts`). The handover changes only `child`, `parent` and `handedOver`, so the worktree never has two lanes and nothing is undone. That one write is atomic per key. `ctx.storage.set` is the host's `kv.set`, a single SQLite `INSERT ... ON CONFLICT DO UPDATE` on one row (anomalyco/opencode `ee5fe34e`, `packages/core/src/kv.ts:49-54`, WAL mode in `database/database.ts:44`). The plugin's key is `plugin:<id>:<key>` (`plugin/host.ts:663-668`).
- The write is a compare-and-set under the worktree's disk lock, which `lifecycle.spawnInto` holds across every server of the repository. It happens only when the stored record is still active and still names the released writer. A second instance that queued behind the first then finds the new writer, so it refuses. It can take over only after a release of that writer by the same rule. Just before the write, still under the lock, the handover proves that the worktree is clean, pushed and at the released `HEAD`. If it changed, the handover voids the release and fails the spawn, and the old lane stays.
- The claim file is written, by rename, just before the record, so no lane record names a writer without its claim. When the record's write fails, the handover puts the released lane's claim back through `syncClaim`, under the same lock, and fails the spawn. A restart between the two writes leaves the released lane as it was and a claim naming the new child. The old lane's next claim sync puts its own claim back, under the same lock, and the next spawn takes the lane over again. A restart after the write leaves one lane, the new writer's. Neither needs repair code.
- `save` and `syncClaim` refuse a copy of a lane whose stored record now names another child (`superseded`). They check under the same lock, so a lifecycle pass that read the lane before the handover cannot put the old writer back. That is the one fence left: the removal-state save in `finalize` fails closed on it, and a refused write stops the removal.

`subagent-worktree` runs git automatically in lanes and checkouts whose config it does not control. So `spawnRunner` in `plugins/subagent-worktree/opencode/src/git.ts` runs `git`, `wt` and `gh` with the environment from `hardenedGitEnv()` in `lib/src/safe-git.ts`. It carries the hardening as `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n` (command scope, like `-c`), so the git calls that `wt` and `gh` make inherit it, and it sets `GIT_ATTR_SOURCE` to the empty tree, `GIT_OPTIONAL_LOCKS=0` and `GIT_NO_LAZY_FETCH=1`. The settings turn off fsmonitor, hooks, the global attributes file, signing and the signature programs, `diff.external`, `core.sshCommand`, `credential.helper` and lazy fetch. The empty attribute source means no worktree `.gitattributes` can select a filter, diff or merge driver. `wt merge` runs with `--no-hooks`, so committed project hooks do not run.

`GIT_NO_LAZY_FETCH` and `GIT_ATTR_SOURCE` need git 2.45, so the plugin reads `git --version` once per process and fails closed: with an older or unreadable git, commands exit 126 with "subagent-worktree needs git 2.45+ for safe automatic merges" and a spawn of an isolated writer is refused. The plugin trusts each repository's local, unversioned `.git/config` and worktree configs, including `includeIf` sections. The hardening covers what versioned content can select, not that config. The plugin reads `git worktree list --porcelain -z` and refuses malformed output.

The divergences of `subagent-worktree` from opencode-plugins are listed under `Approved departures` below.

With git-lfs disabled, an LFS file whose index entry is stale reads as modified. A lane then looks dirty and is kept, never removed.

`plugins/parley/opencode/src/guards.ts` holds the `isRecord` and `strings` type guards that the parley parsers share.

`plugins/parley/opencode/src/test-wait.ts` holds the state-driven test waits: `until` (polls an observable effect, fails after 2 s), `opened` (waits for a round to open) and `quiet` (a few event-loop turns, for "nothing happened yet" checks).

`plugins/autopilot` owns two kinds of state. Run state (`state.<N>.json` generations, `journal.jsonl`, `summary.md`) lives under `<git common dir>/opencode-scratch/autopilot/<run-id>/`. The armed-session index lives in plugin storage (`armed/<sessionID>`). On load, the plugin re-arms from storage. `/autopilot resume` re-binds a run to a new session from its latest state generation. Its tick is an OpenCode automation (a code action created through `tools.opencode.automation_create` that calls `autopilot_status`). An in-process timer covers hosts where that call fails. A run owns one beads ledger, resolved at arm (`resolveLedger` in `plugins/autopilot/opencode/src/ledger.ts`): the `ledger` setup field if given (a `.beads` directory or the checkout holding one), else the ledger the scope's bead id routes to, else the session directory's ledger (`sessionPinFor`, which ignores an inherited `BEADS_DIR`). Routing follows bd's `docs/multi-agent/routing.md`: a ledger's `.beads/redirect` is followed first (first non-comment line, relative to the directory holding the `.beads`, one level); only that resolved ledger's `routes.jsonl` is read, never a parent's; a route prefix must end in `-` (one without matches nothing); the longest prefix that the id starts with wins; `path` is relative to the directory holding the `.beads`, and a routed target's own redirect is followed. A path or route that is no ledger refuses the arm, and so does a `routes.jsonl` or `redirect` that is present but cannot be read safely (a symlink, a special file or over 64 KiB): absent means no routes, unreadable means routing cannot be checked. The ledger is stored in the run state (`ledger`, optional so earlier state files still decode; such a run derives its ledger from its scope and directory as arming would, and has none, so reads and writes refuse, when that fails) and every plugin `bd` call gets it as `BEADS_DIR` in the spawned process's environment, as does the write lock. A write that names a bead whose prefix routes to another ledger, or whose routes cannot be read, is refused. Its own `bd` writes take the embedded-store lock from `lib/src/bd-embedded-write-lock.ts`. Every run state transition holds the lease lock from `lib/src/lease-lock.ts` at `<run-id>/run.lock`, for liveness only. Lease releases check the owner token. State files are versioned and created exclusively: a write of generation N+1 writes its own temporary file and `link`s it to `state.<N+1>.json`, which fails with `EEXIST` when that generation exists. The losing writer journals an issue and the call returns `stale`; nothing is ever overwritten, and there is no write lock or age-based clearing. Readers take the highest generation and validate it with `effect/Schema` (the host's `effect`); a corrupt latest generation is a blocker, never skipped. After a successful link the writer prunes all but the latest five generations. `state.json` is a symlink to the latest generation for people reading the directory; the plugin never reads it. A stop passes through a `stopping` phase until `summary.md` and the handoff bead both exist. Ticks carry a binding token, so a resumed run's old automation goes stale. While a run is armed, its permission hook denies every `ask` and journals it as a blocker, with three exceptions that turn an `ask` into an allow and touch no other effect. An `external_directory` ask for exactly `<root>/*` is allowed when `<root>` is a writer lane's linked, non-primary worktree that `ctx.worktree.list` shows for the project, recorded at a tick with its real path, device and inode (the `worktrees` field of the run state), still a plain directory (`lstat`, not a symlink) with the same device, inode and real path, and free of `*` and `?`; both sides are compared by `realpath`. An `autopilot_merge` ask for `<pr>@<sha>` is allowed under `--allow merge`; the tool then requires a GitHub review `APPROVED` on that head by someone other than the PR author (comments never count), all check runs and statuses green plus every required context (unreadable branch protection or rulesets refuse, and so does a merge-queue ruleset), and a `method` the repository allows. It re-reads the PR's base and head just before merging and refuses on drift, then merges with `gh api -X PUT .../pulls/{n}/merge -f sha=... -f merge_method=...` as an argument array (never `gh pr merge`, so no auto-merge and no `--admin`). Success needs `merged: true` and a `sha`; any non-2xx response is a refusal journaled with its status and message. A final re-read must show a `MERGED` PR at the reviewed head with a merge commit. The third is an `external_directory` ask for `<dir>/*` where `<dir>` is the one export directory the run made last (`review/<head>/<manifest hash>/`, recorded in plugin storage as `review-current/<run-id>`) or a directory under it (`reviewExportAsk`; real paths compared, the directory an `lstat`-plain directory, no `*` or `?`, so a symlink out, a `..` climb, a sibling, `review/` and an older export fail). The host's types (`PermissionEvaluation`: action, resources, metadata, tool call id) give the resource only as an opaque string and carry no read/write distinction, so the grant is on the directory and a session whose rules allow `edit` can write there: the allowed path is model-writable. Integrity comes from the export's manifest, not from the permission. `autopilot_export_review({ pr, base, head })` (`review-export.ts`) runs git as argument arrays in the run's repository with `--no-ext-diff` and `--no-textconv`, rejects revisions that are not strings, start with `-` or hold whitespace, resolves both with `git rev-parse --verify <rev>^{commit}`, and publishes `<run dir>/review/<head-sha>/<manifest-hash>/{manifest.json,round.diff,diffstat.txt,files/<path>}` through a temporary directory. `manifest.json` holds the SHA-256 and size of the diff, the diffstat and every file; its own hash is returned and stored in plugin storage under `review/<pr>@<head>`. Exports are immutable: nothing published is deleted or overwritten, and re-exporting identical content returns the existing directory when `verifyExport(dir, storedHash)` accepts it, otherwise renames the damaged one to `.rejected-<id>` and publishes a fresh one. `verifyExport` refuses a hash mismatch, a changed, extra or missing file or directory, and any symlink or non-regular file. `round.diff` is the three-dot diff `base...head`. Caps (300 files, 4 MiB diff, 512 KiB per file, 8 MiB of content) refuse the export before anything is written, except the per-file cap, which skips and lists the file. Lead-spawned export reviews go to `code-reviewer` (its permissions: `read`, `grep`, `glob` allowed, `external_directory` ask, everything else denied); `pr-reviewer` keeps its contract and gets no export paths. `autopilot_review({ pr, sha })` (`review-session.ts` for the pure parts, the `Autopilot` class for the host calls) lets a merge rest on a verdict the model cannot forge, under the `self-review` grant (default off). It first takes the once-only claim (below), then reads the PR from GitHub (`gh api repos/{owner}/{repo}/pulls/<n>`: `state` is `open`, `head.sha` is `sha`, plus `base.sha` and `changed_files`), refuses when the `code-reviewer` agent (`ctx.agent.get`) is missing, fetches `base.sha` with `git fetch --no-tags origin <sha>` (a failed fetch is tolerated, a missing commit is not), runs `exportReview` against that base SHA and never a branch name, refuses an empty diff or a changed-file count that differs from GitHub's (below), and records the manifest hash as above, then `verifyExport`s against the stored hash, reads `round.diff` through `readBoundedBytes` (cap 256 KiB; the bytes must hash to the manifest's diff entry) and builds the prompt: the diff between lines carrying a random delimiter and labelled untrusted, ending with the exact lines `VERDICT: APPROVE <sha>` and `VERDICT: REQUEST_CHANGES <sha>`. It creates the reviewer with `ctx.session.create({ parentID: lead, agent: "code-reviewer", location, metadata: { source, pr, sha, nonce }, permissions })` (permissions deny `edit`, `shell`, `subagent`, `autopilot_*`), stores a pointer under `review-session/<lead>/<pr>@<sha>` (`pr`, `sha`, `session`, `nonce`, `promptHash`, `manifestHash`, `at`), verifies the export again and sends the prompt with `ctx.session.prompt`; a failure after the create removes the pointer and the session. The call returns at once and does not use `session.wait`. A verdict is never stored: `autopilot_status` (field `reviews`, which also drives the deadline) and `autopilot_merge` derive it with `resolveReview` from `ctx.session.get` and `ctx.session.context` of the child. It requires the child's id, parent (the lead), agent and metadata to match the pointer; exactly one `user` message whose SHA-256 is `promptHash`; no `synthetic` message and no switch to another agent; the last `idle` message and the session `outcome` both `succeeded`, with no user or assistant message after that idle; and the final assistant message (`finish: "stop"`, no error) whose `text` parts, read by `parseVerdictLine` in `lib/src/review-verdict.ts` outside any code fence, end in a `VERDICT:` line whose remainder is exactly `sha`. The verdict line must be the last non-blank line of that text (`parseVerdictLine` with `strict`), so an approval followed by a retraction is none. The turn's finish time from the transcript (the idle message, and the assistant message's `time.completed` when present) must be within 30 minutes of `at`, else the review is void however soon it is polled. Anything else is `void` with a reason. A reviewer without an idle 30 minutes after `at` is interrupted and voided; `autopilot_status` sweeps the lead's pointers with a rotating cursor (below) and shows the newest 20. **Once-only claim:** before any reviewer exists, `autopilot_review` creates two claim files in `<git common dir>/opencode-scratch/autopilot/review-claims/`, beside the run directories so they outlive a run: `pr-<pr>@<sha>` and `head-<sha>` (a head is reviewed once whatever PR number names it). Each is written to a temporary file and hard-linked to its name, so `link` fails with `EEXIST` when it is taken, as for run state generations; a collision releases the claims taken before it and refuses. A claim is released only when the start is refused and no reviewer is left behind, never after a verdict, void, deletion, interrupt or follow-up. A cleanup that fails (pointer or session removal) is journaled as an issue and keeps the claim. The claim files sit in the same scratch area as the run state, so the same-user residual risk below covers them; plugin storage is the second line: before starting, the call scans every `review-session/` key and refuses when any ends in `@<sha>` (any lead, any PR number, any outcome), and a storage read that fails (here, on the pointer read in a merge or a repeated call, on the sweep, on the manifest hash and on the current-export read) refuses the operation, is journaled once as a `blocker` and is listed in `autopilot_status` as `storageErrors`, labelled by operation and resource (`get:<key>`, `scan:<prefix>`, `set:<key>`, `remove:<key>`); a label clears only when that same operation on that same resource succeeds, and a scan label only when that scan completes to the end (a lead-local scan never clears a failed global one). A failure is never taken as no record or as the end of a scan. A sweep cursor that cannot be read stops the sweep (no start-of-list default, no cursor write), and a merge under the `self-review` grant refuses outright when the review record is unreadable, before the GitHub approval is looked at. Pointers are deleted only by a refused start. The export is refused when the recorded diff is empty, and when the number of files in `git diff --name-status -M -z base...head` (a rename counts once, as GitHub's `changed_files` counts it; a deletion-only PR passes) differs from the `changed_files` of `pulls/<n>`. Status resolves the newest 20 pointers and the next 25 after the cursor in `review-sweep/<lead>` (plugin storage, wrapping at the end), so every pointer meets its deadline over successive calls with no cap on how many exist. The run state, the journal and `autopilot_log` are never read for a verdict, and the pointer is only a locator that the transcript must confirm. In `mergeRefusal` the `witnessed` input (`{ granted, approvedSha }`) replaces only the `reviewApproval` check, and only when the grant is set and `approvedSha` is the head being merged; checks, required contexts, the merge-queue and method checks and the head and base drift re-reads still run. Residual risks: prompt injection through the diff can talk the reviewer into `APPROVE` (the fence-aware parse stops a forged verdict line, not a persuaded reviewer); same-user writes to the scratch area, to the host database (`~/.local/share/opencode/opencode.db`) and to the server API are out of scope (they can create or edit sessions and forge a record the plugin accepts); `--allow self-review` is weaker than a second GitHub account; GitHub branch protection that requires approving reviews still refuses the merge. The decisions are pure functions in `plugins/autopilot/opencode/src/policy.ts`. The approval and check judgments are in `lib/src/pr-approval.ts`, which `delivery` also uses; `delivery` keeps its comment-verdict support behind that module's `commentVerdict` option, and autopilot runs the strict mode (review-only approval, `requireKnown` required contexts, `requireBoth` protection and rulesets).

An autopilot scope read counts only when confirmed: for a bead scope, the scope bead is listed and, when the list shows no open work, `bd children` agrees (`readBeads` in `plugins/autopilot/opencode/src/gather.ts`). The read is bounded to 3 attempts within 180 s; after that it is unknown, a blocker is journaled and the run goes on. A read that is unknown never ends the run as "scope finished"; explicit and idle stops still apply.

## safety permission relaxations

`review()` in `plugins/safety/opencode/src/index.ts` wraps `reviewPermission`. When it throws an unexpected exception (handled probe timeouts become `ProbeTimeout`, which the destruction review turns into an ask, so they never reach this path), it returns `undefined` and logs a warning through the plugin's `warn` (`hostWarn`) each time. `applyDecision` treats `undefined` as no change, so the host's own effect (allow, ask or deny) decides; `undefined` never means allow. Both callers (the `execute.before` shell hook and the `evaluate` gate) pass `warn`.

`plugins/safety` turns some `external_directory` asks into allows in `permission.hook("evaluate")` hooks that run before `denyUnanswerable`, because a subagent cannot answer a prompt. Each hook acts only on an `ask`, never overrides a deny, and has a pure decision function tested directly (`scratch-dirs.ts`, `skill-references.ts`, `steering-dirs.ts`, `repo-worktrees.ts`). A hook can be switched off through the plugin's `disable` list:

- `scratch-dirs.ts`: the OpenCode temp folder and the project's worktree folder, for direct file tools and (`scratch-shell`) the `shell` tool. For shell it only waives the `external_directory` ask when every parsed resource lies inside a pinned root; it does not confine the process, which can still read or write elsewhere as any allowed shell can. An empty resource list is never auto-approved.
- `skill-references.ts` (`skill-references`): read-only tools inside listed skills' directories.
- `steering-dirs.ts` (`steering-dirs`): read-only tools inside the `steeringDirs` option, default `~/.config/opencode/steering`, realpath-resolved, user-owned.
- `repo-worktrees.ts` (`repo-worktrees`): read-only tools inside the worktrees of the session's repository. `git worktree list --porcelain -z` runs through `lib/src/safe-git.ts` flags and `lib/src/subprocess.ts` supervision with repository-selecting `GIT_*` variables cleared. Each path must link back reciprocally on disk (`.git` file and `<common-dir>/worktrees/<name>/gitdir`) and be user-owned. Roots are cached 30 s per directory with device and inode and re-checked on every use.
- Roots are compared as canonical paths (`insideCanonical`), never re-resolved after the check.
- `subagent-external-reads` (below) already allows any non-secret read or shell ask in a subagent session, and `root-external-reads` a root session's `read` of one non-secret file. The relaxations above also cover folders and the shell in root sessions; with those two disabled they are what lets a session read these places.

### safety permission.asked backstop

`plugins/safety/opencode/src/asked-watch.ts` owns the second layer of the `subagent-prompts` feature: a plugin whose evaluate hook runs after safety's can still raise a prompt in a subagent session, so `index.ts` subscribes to `permission.asked` and rejects such prompts through `permission.reply`. `index.ts` is a thin adapter: it supplies `subscribe`, the handler (`rejectUnanswerable`) and the warning text; `watchAsked` is the shared loop under another name. With `subagent-prompts` disabled nothing subscribes.

The loop is shared: `watchAsked` is a thin wrapper over the loop in `lib/src/event-watch.ts` (`watchStream`, and `watchEvents` on top of it, which warns by error name and owns the abort controller). Delivery's turn-end retry watcher, autopilot's event loop and model-roles' event loop use `watchEvents` with the same bound, backoff and teardown rules; a handler that throws is warned about (`<label> event handler failed`) and never ends or counts against the stream.

- Retry bound: a stream error, a stream that ends, or a `subscribe()` that throws is one failure. After a failure the watch waits and resubscribes, at most 3 times (4 subscriptions in all). Each failure warns with the error name only (`permission prompt watch failed; resubscribing (attempt N)`); the last one warns `permission prompt watch stopped; …` and the watch ends. The evaluate hook keeps denying.
- Backoff: 1 s, 5 s, 15 s (`DEFAULT_RESUBSCRIBE_DELAYS_MS`; the array length is the bound). `abortableSleep` waits on an unref'd timer and returns at once on abort. A subscription that works resets nothing: the bound counts failures over the plugin's life.
- Teardown: the cleanup function aborts `watching.signal`, then calls `stop()`. Abort ends a backoff sleep, suppresses every warning and ends the loop. `stop()` calls the live iterator's `return()` without awaiting it, because a pending read may never settle, and swallows a rejection from it. A lookup in flight at teardown checks the signal before `permission.reply`, so no reply goes out after teardown.
- Race: the watch is reactive, so a user's answer can land before the reply. Then the reply fails or is a no-op, a failure is warned about, and the user's decision stands.
- Tests: `asked-watch.test.ts` drives the real sleeper with controlled timers; `index.test.ts` injects `sleep` and `delaysMs` through `Overrides.watch`. Neither waits on the wall clock.

## Read-only shell rules and subagent reads

- `lib/src/read-only-shell.ts` owns `READ_ONLY_SHELL_RULES`, the one shell permission list of every read-only agent: `shell "*"` allowed, then a deny list for repository, remote, ledger and file mutations, `git -c`/`--config-env`, and visible redirection (`*>*`, `| tee`). Agent sources put `# {{rules read-only-shell}}` inside `permissions:`; `composeAgent` (`lib/src/fragments.ts`) expands it, and `explore` (`plugins/agent-efficiency`) spreads the list. `tests/read-only-shell.test.ts` keeps every shipped read-only agent in step. The `architect` uses the same list: it writes design and research documents with its edit tool and runs only read-only commands. `pr-reviewer` is not on this list: it reads untrusted PR content and stays on a two-command `gh pr` allowlist.
- Enforcement limit: this is best-effort, the owner's chosen trade-off, not a sandbox. It stops accidental writes by a read-only agent, not a determined one. Prefix and pattern matching can be bypassed by interpreters (`python -c`, `node -e`), nested shells (`bash -c`), `git -C x push` and forms the matcher does not see. Those stay out of scope; do not grow the list into a parser.
- `plugins/safety/opencode/src/subagent-reads.ts` owns the `subagent-external-reads` hook (feature id of the same name, registered before `subagent-prompts`). In a subagent session it turns an `external_directory` ask into an allow for `read`, `glob`, `grep`, `list` and the shell. Edit, write and patch keep the ask. Secrets keep it too: `SECRET_LOCATIONS` (exported), `*.env` and `*.env.*`, plus the `subagentSecretPaths` option. Limits: paths resolve through `realpath` before any check; a resource that is inside or an ancestor of a protected location (`~/*`, `/*`) is refused; a relative path, a mid-path wildcard or `..` keeps the ask. A root session gets a narrower grant through `root-external-reads` (same file, feature id of the same name): `read` of one file whose given path (`path`, or `filePath` on older hosts) is absolute, is a regular file and is no secret by the same rules. `glob`, `grep`, `list`, the shell and the writers keep the ask, since a folder's name says nothing about the `.env` files or secret links inside it; a failed session lookup keeps it too. `disable: ["root-external-reads"]` turns it off; `disable: ["subagent-external-reads"]` turns the subagent half off.
- `scratch-dirs.ts` also allows the session directory spelled through a symlink alias, `<data>/opencode/shell/<project id>` and `<data>/opencode/tool-output`.

## OMP agent translation

`scripts/omp-agents.ts` translates the OpenCode form of every agent, composed or vendored, into `common/agents/<id>.omp.md`. The build skips an agent whose `<id>.omp.md` someone wrote by hand. For a plugin that lists `omp`, harness-kit copies that file to `omp/agents/<id>.md`. The translation keeps `name`, `description` and the prompt body. It drops these keys:

- `mode`, `steps`, `hidden` and `color`
- the fallback `model`
- the request headers, after it reads the tier from them

`model:` lists OMP role aliases, tried in order. OMP 19.1.1 skips a role the user has not assigned: an agent whose first role was unset ran on its second.

| Tier | `model:` | Reason |
|---|---|---|
| `cheap` | `@smol` | the built-in OMP fast role, and the tier's old role name |
| `standard` | `@task` | the built-in role for task subagents, and the tier's old role name |
| `strong` | `@slow` | the built-in strongest role, and the tier's old role name |
| `reviewer` | `@challenger, @slow` | OMP has no built-in review role. `challenger` is the tier's old role name, assigned to a model from another vendor. When it is unassigned, the tier falls back to `strong`, as in model-roles. |
| `orchestrate` | `@orchestrate, @slow` | OMP has no built-in role for it. It falls back to `strong`, as in model-roles. |

`judge`, the other old name of `reviewer`, is not used: OMP defines `judge` as a model-kind role for judgment runners, not a chat role.

Three `x-omp-*` keys in `agents.src/<id>.md` steer the OMP form only. The build takes them out before it composes the OpenCode form, because OpenCode reads a file with an unknown key as V1. Each key is one line:

| Key | Effect | Used by |
|---|---|---|
| `x-omp-model` | OMP roles that replace the tier's `model:` | `architect` and `concept` (`@architect, @slow`), `ui-ux-specialist` and `ui-implementer` (`@designer, @slow`), `spec` (`@plan, @slow`) |
| `x-omp-shell` | why a read-only agent keeps `bash` and `eval`, written into the generated comment | agents whose prompt runs commands, such as `code-reviewer` (`git diff`) and `researcher` (`bd`) |
| `x-omp-tools` | OMP tools to add that no OpenCode permission stands for | `pr-reviewer` (`github`) |

The OMP `tools` key is an allowlist of built-ins. OpenCode allows an action that no rule names, so the translator reads a `permissions` list on top of that default. Every shipped agent starts from a deny-all rule. `journey-validator` has only deny rules, so it gets every built-in it does not deny. Only an agent with no rules keeps the OMP default tools. Each unrestricted allow maps to built-ins:

| OpenCode action | OMP tools |
|---|---|
| `read` | `read` |
| `grep` | `grep`, `ast_grep` |
| `glob` | `glob` |
| `lsp_*` | `lsp` |
| `edit` | `edit`, `write`, `ast_edit` |
| `shell` | `bash` |
| `execute` | `eval` |
| `websearch` | `web_search` |
| `subagent` | `task`, with the allowed agents in `spawns` (`explore` as `scout`, `general` as `task`). OMP gives every agent `wait` itself. |

When no tool is left, the file says `tools: []`, because an empty value means the OMP default tools.

OMP has no per-resource rules, no per-agent ask and no per-agent skill filter. The translator keeps a tool whose unrestricted rule allows it and drops that tool's per-resource rules. It leaves out a tool whose unrestricted rule asks. It also leaves out a tool that only per-resource rules allow. An agent whose edits OpenCode limits to some paths therefore gets no edit tool: `concept` and `spec`. A generated comment at the top of each file lists every dropped rule.

A read-only agent has no OMP edit tool. The translator also leaves out its `bash` and `eval`:

- OMP cannot hold the per-command deny list of `READ_ONLY_SHELL_RULES`.
- `eval` reaches the shell through `sh()`.

Either tool would let the agent write. `x-omp-shell` keeps them for an agent whose prompt needs a command, and the generated comment states that reason. The comment is not part of the prompt, so the translator also opens the prompt with a notice: the shell is not restricted to read-only commands, nothing enforces the limits in the instructions, and the agent keeps to them itself.

OMP merges agents by name, and the first one found wins. A plugin agent also replaces a bundled OMP agent of the same name. The bundled agents are these:

- `scout`
- `reviewer`
- `security-reviewer`
- `task`
- `sonic`

OMP has no plugin dependency, so `researcher`, `pr-reviewer` and `adversarial-challenger` each ship from two plugins. `ompNameConflicts` makes `bun run build` fail in two cases:

- The OMP files of one agent in two plugins differ in more than the source comment.
- A plugin agent takes a bundled name.

The second case explains the name `security-auditor` in `agent-reviewer`. Named `security-reviewer`, it would replace the bundled OMP agent for every `task` caller without warning. The bundled agent returns structured output and has no shell, and the two serve different purposes.


## code-challenge

`plugins/code-challenge` is OpenCode only (`harnesses: ["opencode"]`). It challenges existing code for simplification, performance, stability, hand-rolled code and structure, and plans only: it edits no source file.

- Ownership: the plugin owns the `code-challenge` skill (thirteen lens references, the report and decisions JSON Schemas, intake, scoring and run-storage rules), the `/code-challenge` command, the `challenge_setup`, `challenge_lib_facts`, `challenge_validate` and `challenge_scan` tools, nine beads formulas and the `code-challenger` and `refactor-challenger` agents. `challenge_scan` is documented under Code-challenge scan.
- Run storage: every run writes under `<git-dir>/code-challenge/<run-id>/`, outside the working tree (`intake.json`, `scan.json`, `findings.json`, `research.json`, `verdicts.json`, `decisions.jsonl`, `report.json`, `report.md`). `decisions.jsonl` is append-only. The directory is never committed.
- Formulas: `challenge_setup` copies `code-challenge` (the full run), `mol-challenge-<phase>` for the seven phases and `mol-challenge-lens` into `.beads/formulas/`. The lead agent sequences the phases, dispatches subagents and writes every file, bead and log line. Only `mol-challenge-lens/analyse-lens` (to `code-challenger`) and `mol-challenge-refute/attack-findings` (to `refactor-challenger`) route to a subagent. Both agents are read-only; each routed step lists `requires_actions` and a test checks the agent's permissions allow them.
- `challenge_setup` resolves the target workspace from the invoking session's directory and fails when it cannot read that session.

### code-challenge `read-grant.ts`

`plugins/code-challenge/opencode/src/read-grant.ts` (`referenceReadRules`) lets both challengers read the skill's reference files without a prompt, because an installed plugin's skill sits outside the project and a subagent cannot answer an `external_directory` ask.

- Scope: exactly `<skills root>/code-challenge/references/*`, as an `external_directory` allow. `SKILL.md`, the skill's parent, other skills and the project are not covered.
- Fail closed: the grant is made only when `realpath(references)` equals `realpath(skills root)/code-challenge/references`. A symlink to the parent or outside, any other mismatch, or a missing directory means no grant and one warning.
- The rules are built once at setup from the two validated paths with `directoryReadRulesFor` (`lib/src/agent-files.ts`), which never touches the file system, so no second resolution can add a pattern.
- Trust assumption: the check is a single point in time at setup. A later swap of `references` is bounded by the validated pattern, but the host follows symlinks when it reads, and that is outside this plugin's control; the install directory is assumed writable only by the installing user.

### code-challenge `challenge_validate`

`plugins/code-challenge/opencode/src/validate.ts` registers `challenge_validate`. It takes the absolute run directory, reads only `report.json` and `decisions.jsonl`, and checks them against the shipped schemas with `opencode/src/json-schema.ts`, the small in-repo validator that already guards the schemas in tests (it throws on a keyword it does not know). No JSON Schema library is added.

### code-challenge `challenge_lib_facts`

`plugins/code-challenge/opencode/src/lib-facts/` registers the `challenge_lib_facts` tool (`registerLibFacts(ctx)`). It returns facts about 1 to 6 packages (npm, PyPI, crates.io, Go) and no verdicts, and uses `fetch` with no HTTP library.

- External sources, all HTTPS: `api.deps.dev` (v3, and v3alpha for dependents), `registry.npmjs.org`, `api.npmjs.org`, `pypi.org`, `pypistats.org`, `crates.io`, `proxy.golang.org`, `api.osv.dev` (`querybatch`) and `api.github.com`. Each source can fail alone; the failure is listed in the package's `missing`.
- OSV is never cached. An OSV reply with a wrong result count, a continuation token or a malformed vulnerability list is a failure, so the CVE gate reads `null` instead of passing.
- GitHub token boundary: the tool runs `gh auth token` itself (5 s timeout) and sends the token only as the `Authorization` header of requests to `api.github.com`. It is never logged, returned or cached. Redirects are followed by hand and only within the original host. Repository URLs come from publisher metadata, so only recognised github.com forms are used, `owner` and `repo` must match GitHub's charset, and each part is `encodeURIComponent`-ed into the path.
- Input limits: package names are checked per ecosystem (no `?`, `#`, `..`, control characters or backslashes; at most 214 characters) and versions must be plain version strings.
- Cache: one JSON file per request under `$XDG_CACHE_HOME/opencode/code-challenge/lib-facts` (`~/.cache/...` by default), 7-day TTL. GitHub replies are reduced to the public figures the tool reports before they are stored, and a cached value of any other shape is a miss. File names carry a schema version (`v2-`); files of any other version are never read and the sweep deletes them. A file over 256 KiB (measured in UTF-8 bytes) is neither written nor read, and an entry that fails its shape check is deleted. An expired entry is deleted on read, and the first write of each call sweeps expired files and trims the directory to 2000 entries.
- Request limits: 6 requests in flight, a 10 s timeout each, 5 MiB per reply (checked while streaming, before `JSON.parse`) and 3 same-host redirects.
- Licence gate: `ALLOWED_LICENCES` in `licence.ts` lists permissive and weak-copyleft SPDX ids. `spdx-expression-parse` evaluates expressions with grouping, `AND` and `OR`; it is a small, widely used parser (the one `npm` tooling uses) and replaces a hand-written grammar that mishandled parentheses. It is inlined into the bundle like `jsonc-parser`.

## Code-challenge scan

`plugins/code-challenge/opencode/src/scan/` is the `challenge_scan` tool module of the SCAN phase. `registerScanTool(ctx)` in `scan/index.ts` registers the tool and a permission hook, and returns one dispose function. The module adds no runtime dependency.

- `recipes.ts` is the recipe table: for each existing analyzer, its language, lenses, arguments, accepted exit codes, parser, whether it needs a build (quick depth skips those), how it is installed and whether it runs repository code. It uses no custom rules. `parsers.ts` turns each tool's output into hits; output that is not in the tool's format is a coverage gap, never "no findings".
- `run.ts` plans (language, lens, depth, repository markers, tool resolution, consent), then executes each recipe and returns candidates, coverage (`ran`, `skipped`, `gap`) and per-tool timings. `probes.ts` computes `ruleEnabledInRepo` for ruff (one `--show-settings` per config) and golangci-lint; every other tool reports null.
- Each lens profile ignores the repository's rule selection (`--isolated`, `--no-config`, a temporary config, or `-A clippy::all`) but keeps `.gitignore` and inline suppressions. Biome ignores `--config-path` when the root has a `biome.json`, so then it runs from its own config directory on an explicit list of files that git does not ignore.

### Provisioning and pins

- Nothing installs globally. A recipe uses the binary on `PATH`, else a one-off `bunx -p`, `uvx --from` or `go run` of an exact pinned version from `scan/pins.ts`. A missing tool is a coverage gap.
- `eslint` and `@e18e/eslint-plugin` must sit side by side, because the plugin resolves from the config file. The scan never installs them: it reports the pinned `bun add` command and looks in `<git-dir>/code-challenge/tools`, where it also writes the eslint config.
- Renovate moves the pins through the manager for `pins.ts`. Bump a pin together with a run of the recipe's command, because a flag can change between versions.

### Trust and consent

- There is no sandbox, by user decision. The scan discloses what it runs and asks for consent, per canonical root, before it runs anything that is not static analysis: clippy (build scripts and proc macros, writes `target/`), golangci-lint and deadcode (compile Go, may fetch modules), knip and import-linter (load repository config code), and every one-off `bunx`, `uvx` or `go run`. Without consent those recipes are coverage gaps with the reason; recipes that run no repository code still run.
- Consent is an approved set, not a flag. The tool computes the risky recipes (`consentRisks`), asks once through `permission.assert` with the resource `<canonical root> [<sorted recipe ids>]` (so a saved approval covers exactly that set), and passes `ScanDeps.approved` (a set of recipe ids) to `runScan`. A risky recipe outside the set is a gap, "not approved for this run"; a plan with no risky recipe approves nothing and asks nothing. `approved` is host-side only; tool input cannot set it. `confirmScan` turns an allowed scan with risky recipes into a prompt that lists them.
- Every rejection of the prompt (deny rule, feedback, interruption) propagates as the host defines it, as in `dep-update` and `safety`. The voluntary way to scan without the risky recipes is the `staticOnly` input, which asks nothing.
- Analyzer processes get an allowlisted environment (`env.ts`): `PATH`, `HOME`, `TMPDIR`, locale, toolchain and cache variables, proxy and CA variables. Variables whose names look like credentials, and `AWS_*`, `GH_*` and `GITHUB_*`, are dropped, even under an allowed prefix such as `UV_`.
- File names reach tools as absolute paths after `--`. Every named path and glob is resolved with `realpath` and must stay inside the canonical root. Symlinks met while walking or globbing are skipped. A run id is one path segment (`^\w[\w.-]{0,63}$`).
- Output directories are created one real directory at a time, files are written with `O_NOFOLLOW`, and a symlink in the way is refused.
- Captured stdout (16 MiB) and stderr (1 MiB) are capped and an overflow ends the tool's process group; report files and marker files are `lstat`ed and size-capped; the per-tool timeout is capped at 900 s.
- Accepted residual risk: races on parent path components that need concurrent local filesystem control (swapping a directory for a symlink between the check and the use) are not defended. The model is a trusted local repository with no sandbox, by user decision.
- Tests: the Biome behaviour suite always runs (biome is a devDependency, resolved from `node_modules/.bin`). The ruff and golangci-lint suites in `scan/behavior.test.ts` skip with a printed reason when the binary is absent, and no workflow installs them, so CI skips them; they run on a machine that has them.

## agent-efficiency restart nudge

`plugins/agent-efficiency/opencode/src/restart-nudge.ts` is a stopgap for upstream restart recovery, which posts the "Command cancelled because the server restarted" notice with `resume: false`, so an idle subagent that waited on the lost shell never wakes.

- Option: `restartNudge`, off by default; `true` or `{ graceMs }` (5000 by default). `index.ts` calls `setupRestartNudge` only when `parseRestartNudgeOptions` returns a value, and pushes its cleanup onto the plugin's disposers.
- Behaviour: `setupRestartNudge` subscribes to `session.synthetic` events. A restart notice starts a timer; after `graceMs`, `createRestartNudger` reads the session and, when `needsNudge` holds (not archived, not running, last run ended before the notice), posts one `resume: true` synthetic message. The message text does not contain the notice text, so a nudge cannot trigger another.
- Lifecycle: a session stays reserved from its notice until its attempt ends, and is nudged at most once per plugin process. State is in memory only. The cleanup returned by `setup` aborts the subscription and disposes the nudger; a disposed nudger ignores later notices and an in-flight lookup posts nothing. A failed subscription is logged with its cause through `console.warn`; an abort is silent.
- Decision logic (`needsNudge`, `isRestartNotice`, `createRestartNudger` with injected `schedule`) is pure and tested directly; `setupRestartNudge` is the adapter.

## delivery: cleanup in another repository

`delivery_land` with `repo` and a clone (`repoPath` or a `worktree`) keys the receipt by the target repository. Every later cleanup of that receipt runs in the clone. This covers the inline cleanup, an explicit `delivery_cleanup` and the turn-end retry. `repositoryCoordination` in `plugins/delivery/opencode/src/pending-cleanup.ts` binds the cleanup to the target. `cleanupDelivery` takes it as `CleanupDeps.coordinate`.

- Delivery reads and writes the coordination files under the target's git common directory: claims and landing records, holds and denials, and the removal lock.
- If the clone now resolves to another common directory, delivery removes nothing.
- The final checks wait on listings, so right before the removal call delivery proves both `.git` markers again, synchronously. It checks the worktree's and the directory the removal runs from, and refuses if either changed.
- The last check lists the sessions in the worktree across all projects.
- If the sessions in the clone and the worktree name exactly one project id, delivery removes the worktree through OpenCode's registry. With any other answer it refuses the removal.
- `cleanupDelivery` without `coordinate` still refuses another repository.

The clone registry is `<receipts root>/.clones/<session repo key>.json` (`clone-registry.ts`), a JSON list as 0.10.5 wrote it. It lists, newest first, each repository that the session's repository landed into. An entry has the key and canonical root of that repository. It can also have its common directory and its `owner/name`. It can also list the receipt ids landed there, with the time.

The turn-end pass and an explicit cleanup drop the settled ids. An entry with no id left goes once gc collects the landing records of the target. The turn-end retry reads the registry, and so does gc. Each one checks the key of a root again first. Each update takes a lease lock (`lib/src/lease-lock.ts`) beside the file and replaces the file by rename.

Past 32 entries, the oldest entries that need no registration go. An entry stays whatever the count when it has pending receipts, when a landing record of its target repository is not collected yet, or when those records cannot be read (`registrationNeeded`): once the registration is gone nothing else would find the records. An older entry with no common directory follows the count rule.

Each plugin instance also keeps the clones it registered in memory, and those win over the file. A failed write leaves its retry intact. A landing record reaches the target before the registry write starts.

### Running reports

`lib/src/running-reports.ts` (shared by the OpenCode plugin and the pi/OMP extension) keeps what each session last reported as running, one file per session and server instance: `<receipts root>/.running/<sha1(session id)>.<sha1(instance)[:16]>.json` holds `{sessionID, jobs, at, pid, host, instance, gen}`. `instance` names the writer: the server process (`host:pid:start`) plus, in the OpenCode plugin, a random nonce made at each activation (`createPendingCleanup`), so a reload in the same process is a new writer with its own `gen` counter, `unsettled` and `pendingDeletes`. `gen` is that writer's own generation of the report. An activation writes, clears and deletes only its own file, so no two writers share a file and no ordering between instances is needed: a session holds when any live instance's file has a matching job. The format is unchanged from the single-file layout apart from `gen` (absent reads as 0) and the extra name segment, so older readers, which scan `*.json` and parse each file by its content, still see every file (checked against the round-1 `readReports`). A file kept under the old un-suffixed name is still read; no activation deletes it, because none wrote it: it ends by pid liveness or expiry. The idle hook writes first, before any git, registry or receipt work, and decides nothing at write time: no repository, clone listing or session lookup is needed to record a report.

Threat model: the receipts root belongs to one machine, and any OpenCode server on that machine may write it. On this host a report's liveness is its reporter's pid alone, however old its file is. A report from another host cannot be judged by pid, so it holds until it expires, measured on the reader's clock against the file's mtime. Clocks across hosts are not trusted, so `at` only orders one session's writes.

Atomicity: every write, clear and removal of a report takes one lease (`<receipts root>/.running.lock`, the `lib/src/lease-lock.ts` helper the other coordination writes use), and a write is a temp file and a rename. Ordering is per activation only: it comes from the activation's local per-session generation (below), and only the current generation writes or clears, so a stale completion does nothing. There is no ordering across activations or instances, because they never touch each other's files, and no timestamps are compared between them, so a clock tie or a clock going backwards cannot undo a report. A removal takes the lease at its last read of the reports and keeps it until its removal section ends, so a report that arrives meanwhile waits. The lock order is always the worktree's removal lock, then the store lease; no writer takes the worktree lock while it holds the lease. Reads are bounded: a report is read as a small regular file only, so a FIFO, a device, a symlink or an oversized file makes the store unreadable instead of stopping the check.

Only the reporting session clears its report, and only in its own instance: an empty job list unlinks the instance's own file under the lease (there are no tombstones), and `session.deleted` unlinks it too. Each session has one in-memory `unsettled` record, `{gen, at, reason, failed, background}`. The idle hook sets it synchronously, before any await, with a new `gen`, the report's stamp and the job list (reason: waiting). Only a write or clear of the current `gen` that succeeds deletes it; a failure, a lease that cannot be taken included, sets the reason and keeps it, and a completion of an older `gen` changes nothing. `session.deleted` deletes the record at once. If the file cannot be removed (no lease, a refused unlink) the session goes into `pendingDeletes` with the session's generation at the deletion as its token, retried by the same triggers as the snapshots below. A retry, under the lease, unlinks only when no newer incarnation of the session has begun here and the file on disk carries a generation no higher than the token, so a session id that is reused and writes meanwhile keeps its live report. A retry removes its `pendingDeletes` entry only when the stored token is the one it used, so a newer deletion's token is never dropped. Dispose sets a `disposed` flag that every queued clear, empty write, delete and retry checks under the lease, so that work does nothing after it. A non-empty write is always published, even after disposal: a hold written late is harmless, because it ends with the pid. A plugin lifecycle event never deletes a report: neither setup nor dispose removes any file, because OpenCode keeps several Locations (several activations) alive in one process (`packages/core/src/location-services.ts`) and background shells outlive plugin disposal and are not replayed to a new setup (`packages/core/src/shell.ts`). A report ends by its own rules: its writer clears it, its pid dies, or (another host) it expires. A session that moves between Locations leaves its old activation's file behind: no activation ever writes, clears or deletes another's file (in particular a new snapshot does not supersede another activation's file, because a descendant's shell job is marked cancelled before the shell exits, `packages/core/src/session.ts`, `job.ts`, `shell.ts`, so a fresh snapshot can omit a shell that still runs). The old file holds while its pid lives, that is until process exit, which fails closed. Grace window: the host marks a job cancelled before its shell exits (`packages/core/src/job.ts`, `shell.ts`), and stops a shell with SIGTERM, then SIGKILL after `STOP_GRACE` = 3 s (`shell.ts:52`, `:372-388`), so a job that leaves a session's job list may still be running. Each activation remembers, per session, the jobs of its last snapshot. A job that disappears from the next snapshot stays in the written report with `endedAt` set (older readers ignore the field and read it as a running job), for `GRACE_MS` = max(10 s, 3 s + margin) = 10 s. An empty snapshot therefore writes the ended jobs and clears only when none is left; a snapshot, a pass, check or idle retry (the same triggers as the other retries) or the writer's timer, that finds every ended job's window over, clears the file. `session.deleted` does the same: the deletion marks the file's jobs ended at once and unlinks the file only once the window is over (a snapshot that never reached the disk holds nothing). The host does not report the directory a shell really runs in (a shell may run elsewhere than its session, `packages/core/src/tool/plugin/shell.ts:407-414`), and the report guesses none: a job with no recorded cwd is judged by the removal's own rule, so one that names the worktree in its command holds, one whose owner session works inside it holds, and one that cannot be placed holds (a remover without session lookup, Pi, holds every such job). The missing-session shortcut (a report of this server whose own session the host no longer has holds nothing) applies only to jobs without `endedAt`: an ended job holds whatever became of its session, because its shell may still be stopping. A job that has ended past its window stays in the file until cleared, so the clearing must come: besides the triggers above, the writer sets one one-shot timer, unref'd so it never keeps the process alive, at the earliest `endedAt + GRACE_MS` of the report it wrote (a deleted session's pending delete included). It runs the same retry and clear paths under the lease and the usual generation rules, and disposal cancels the timers. Known limit, not new: the host stops a shell by signalling its process group (`process-daemon` `unix.rs:215-231`), so a detached descendant that left the group is not stopped with it and is not seen by any report. Reload and Location moves: a reload in one process, or a session that moves between Locations, strands the old activation's file, which holds while the pid lives, that is until process exit; accepted as fail-closed. A pending delete is no hold of its own, because the report file itself holds while its pid lives, which fails closed. A write or clear still in flight for a session with no record, or a newer `gen`, writes nothing and recreates no record. A report waiting on the lease is therefore already a hold on every removal. `unsettled`, the job memory (`reported`) and `pendingDeletes` are activation-local: another activation, or another instance, has its own, and nothing is shared: when the store cannot be written, the other instance's own read and write probe fails too. A report whose write failed is written again from its stored snapshot, under the same `gen` rules, at the start of every pass, in the removal's check before it looks at `unsettled`, and by any session's idle hook (each trigger is tested alone through the `retryAt` seam), once the store accepts a probe write; a success settles the entry.

A removal asks last, under the removal lock, after the claim, `holdsState`, denial and busy-session checks. It holds when any session is `unsettled`, when the reports cannot be read, when the store cannot be written, or when a live report names the worktree. A report of this server always counts, and one of another server on this host counts while its pid is alive, whatever its file's age; one from another host counts until its file is older than `HOLD_EXPIRY_MS` on the reader's clock. For a report of this server, "its session is not found" also counts as dead; for another server's report it never does, because this host's sessions say nothing about it. The host's idle list gives each job the session that owns it (and a shell its `command`), and no working directory: so a job holds when its command contains the worktree path (raw or canonical), when a recorded `cwd` is inside it, or, with no recorded cwd, when a session it names works inside it, cannot be located (a failed or timed-out lookup, or no directory), or was not looked up; a job that names no session has no cwd to establish and holds. A session this server does not have is skipped. The reports are read once, the sessions looked up, and under the lease the lookups are made again for every report whose time or jobs changed. Only then, with nothing awaited after it, are `unsettled` checked and the reports read for the decision, because an idle hook marks its session without the lease. The removal's last check, `beforeRemoval`, is synchronous and runs right before the removal is dispatched, after the last proof, with no await between it and the call: it refuses when a session was marked since the final check.

The final check gets every verified spelling of the worktree (git's registered path, the receipt's own path and the canonical form of each) and matches a job's command and cwd against all of them.

Bounded waits: the host's worktree removal takes no `AbortSignal`, so a removal that never answers cannot be cancelled. The removal therefore keeps the lease until it settles, since letting go early could delete a worktree a report has just claimed. Every other wait is bounded instead. A writer waits at most the lease's wait, then its report stays `unsettled` (a hold) and the idle hook goes on. Another removal that cannot take the lease in that time refuses and defers its pass. The idle hook waits at most `IDLE_PASS_MS` for the pass it starts; the pass stays in the serial chain and finishes later. Disposal waits at most `DISPOSE_WAIT_MS` for the chain, then returns without letting go of the lease a live removal still holds: the pid and stale rules of `lease-lock` reclaim it once the process is gone.

Pi and OMP: `delivery_cleanup` in `plugins/delivery/pi-src/delivery-cleanup.ts` reads the same reports under the same lease (`runningLeaseFile`, one helper for both hosts; `holdLease` in `lib/src/lease-lock.ts` takes it). The lease is taken by the final check, after the final proofs and inside the worktree's removal lock, and kept until the removal ends (lock order: worktree lock, then lease). The check matches git's registered path and the receipt's raw and canonical spellings. It has no session lookup, so `blockWithoutSessionLookup` holds a job that records no cwd and does not name the worktree, whatever session it names. A report is live by its pid on this host and by expiry on another host.

No TypeSpec contracts exist in this repository (no `.tsp` files or `tspconfig`). The schema of a running report is `parseReport` plus the exported `RunningReport` type in `lib/src/running-reports.ts`, and nothing else: every read in the OpenCode plugin and the pi/OMP extension goes through `readReports`, which parses each file with it. A file that is not a small regular file, or that does not parse (a wrong type, a non-positive or fractional pid, an empty host, a job field that is not text), makes the store unreadable, and an unreadable store holds every removal. The clone registry and the claims files are still hand-parsed in their own modules.

Known gap: `subagent-worktree`'s lane owner does not read the reports. `running-reports` now lives in `lib/`, so it can import it and read them (bead `harness-plugins-ayy`); that change is not made here.

## CI

`.github/workflows/ci.yml` runs on pushes to `main`, pull requests and `workflow_dispatch`:

- `repo-checks` installs bun and just with `jdx/mise-action`, runs `just install`, then the recipes `lint`, `build-check`, `plugin-table-check`, `steering`, `pitfalls`, `agent-roles`, `descriptions`, `concerns`, `release-prepare-check`, `test-executables` and the Python unit tests of the shipped scripts. `release-prepare-check` (`scripts/check-release-prepare.ts`) makes the delivery bundle stale in a temporary checkout, runs its release prepare step and fails if a bundle is still stale.

`renovate-regenerate.yml` accepts only `opened` and `synchronize` events from `renovate[bot]`, for that bot's same-repository PRs on `renovate/` branches. Both job guards reject forks. It skips heads whose commit subject is `chore(deps): regenerate generated copies`.

The build job has only `contents: read`. It checks out the event's head SHA without persisted credentials, runs `bun install --frozen-lockfile`, then `just build` and `just check`. It uploads a generated-file patch. SHA-pinned first-party upload/download actions transfer that patch within the same workflow run. The push job uses a separate runner with `contents: write`, `pull-requests: read` and `actions: write`. It runs no bun or just command or repository code, and checkout persists no credentials.

Both jobs validate the patch against the workflow's generated-path allowlist. It covers inventories, manifests, harness copies, bundles, runtime copies, shims, Claude hook output and composed/translated agents. Composed agents require a matching `agents.src/` file. Translations require an existing OpenCode form. The validator accepts UTF-8 text only and rejects binary data, symlinks and special file modes. Executable harness copies must match their `common/` source's mode. Bundles cannot acquire execute bits. The push job checks paths and modes in a temporary Git index before applying the patch to its checkout.

`renovate.json` ignores that bot's exact author email through `gitIgnoredAuthors`. Renovate can then rebase or update branches containing regeneration commits.

The push job commits as `github-actions[bot]` with Git hooks disabled. Branch names pass through quoted environment variables, not shell-source interpolation. If the remote head moves, the job leaves regeneration to the next run. Git's fast-forward check prevents overwriting a concurrent push.

After pushing with `GITHUB_TOKEN`, the job dispatches `ci.yml` on the PR branch through the REST API. GitHub [returns the created run ID](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event). The job then explicitly dispatches `ci-publish.yml` on the default branch, passing only that run ID.

Both dispatches use GitHub's [documented dispatch exception](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-when-your-workflow-runs/triggering-a-workflow). Other token-triggered events do not start unattended workflows. The publisher must not depend on a `workflow_run` event from token-dispatched CI. Pull request runs from pushes made with `GITHUB_TOKEN` [need approval](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-when-your-workflow-runs/triggering-a-workflow). These dispatches need no approval, App token or PAT.

GitHub [excludes dispatched job checks from PR checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/defining-the-mergeability-of-pull-requests/troubleshooting-required-status-checks#checks-from-some-workflow-jobs-are-not-evaluated), even on the correct head SHA. `ci-publish.yml` publishes [commit statuses](https://docs.github.com/en/rest/commits/statuses) named `check / check` and `repo-checks` on that SHA.

The publisher accepts `workflow_dispatch` only on the default branch. It runs inline code, with no checkout, install, artifact download or cache. Its job has `statuses: write` and read access to Actions, contents and pull requests. It validates the numeric run ID and accepts only the latest CI dispatch for an open, same-repository Renovate PR whose current head matches the run.

The CI definition on the branch must match the publisher's default-branch revision, except for version updates at approved `uses:` entries. These are the harness-kit check workflow tag and SHA pins for checkout, setup-node, setup-bun and mise-action. The publisher rejects changes to steps, conditions, permissions or action repository names.

A running dispatch receives pending statuses. The publisher polls every thirty seconds for up to twenty minutes, then fails if CI has not completed. Success needs a successful run and both required jobs succeeding. Failed, canceled, missing or skipped required jobs produce failure statuses. Repository Actions approval settings remain unchanged.
After manually dispatching or rerunning CI, dispatch the publisher again on the default branch with the CI run ID: `gh workflow run ci-publish.yml --ref main -f run_id=<ci-run-id>`. No PR rebase is needed when its CI definition still matches the publisher's checks.

`.github/workflows/release.yml` runs on pushes to `main`. It calls the harness-kit release workflow, which runs multi-semantic-release (`release.config.mjs`, `.multi-releaserc`) and tags each plugin `<name>--v<version>`. The `prepareCmd` from `scripts/release-preset.mjs` (used by `release.config.mjs`) runs `scripts/build.ts <name>` after `harness-kit stamp`, because a bundle can embed its plugin's `package.json` (delivery's receipts carry the version) and the release commit must carry the rebuilt `opencode/dist`. A `feat` or `fix` commit, and with the repository rules a `refactor` or `docs` commit, under `plugins/<name>/` cuts a release. A new plugin needs no manifest entry: any directory under `plugins/` is a workspace package.

The reusable workflow publishes each released `pi/` tree to npm through trusted publishing (OIDC). `release.config.mjs` enables the preset's `publishPi`. The caller passes `npm-publish: true` and grants `id-token: write`. npm 11.5.1 or later handles publishing without a stored npm token. Set each npm trusted-publisher link to this caller workflow: `release.yml` in `srobroek/harness-plugins`. The publish command runs inside one of its jobs.
