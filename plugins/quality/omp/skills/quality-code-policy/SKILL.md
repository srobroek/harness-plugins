# Maintainable code

MUST Load the `quality-code-design` skill (and only its task-relevant references) for adding new behavior or a capability, a refactor, a hard bug whose root cause remains unclear after reading the failure, or a code review. Small edits, mechanical changes, test-only fixes, config, docs and command runs do not need it. Read-only roles stay read-only.

MUST Prioritize SOLID, encapsulation, and protected invariants over YAGNI when they protect a real responsibility or boundary, using the language's own idioms. A library, ORM, or boundary with one consumer is justified when it reduces present total complexity; consumer count alone decides nothing.

MUST Apply DRY to knowledge that must change together, not to code that merely looks alike. Revisit structure whenever behavior changes.

MUST In every project, author each serialized or published contract you own in TypeSpec, even when it stays within one process, language, or repository. Use `@typespec/http` and `@typespec/openapi3` for internal and external HTTP APIs. Use `@typespec/json-schema` for config, file and record formats, CLI and tool JSON output, event and message payloads, and MCP tool input and output schemas. Keep `.proto` for protobuf and gRPC wire contracts and GraphQL SDL for GraphQL APIs. Keep channels and bindings in AsyncAPI and reference the emitted payload schemas until a stable TypeSpec AsyncAPI emitter is available. Vendor third-party schemas as published; do not re-author them. In-memory types that are never serialized or published are out of scope. Generate and commit the applicable artifacts, and generate OpenAPI, JSON Schema, API reference docs and reference documentation from the same source; never edit generated output by hand. Never hand-write a model class, Zod schema, serde struct or Go struct for such a contract: change the TypeSpec and regenerate, with the pinned routes in `toolchain-api` and `lang-<language>-libraries`. Report any other departure with its reason. Rules, known issues and the CI gates: `quality-code-design`'s `contracts.md` and `toolchain-api`.

MUST Use OpenFeature through one flag module with one provider over flags.yaml, SSM or AppConfig, chosen by need; ask before writing a missing provider. Decide once at the request or job edge and default to existing behavior. Libraries take caller decisions; plugins keep harness-specific options. See `quality-code-design`'s `feature-flags.md`.

MUST Before designing or writing code for a concern, research current best practice (official docs, Context7 when configured for the project, or the web) and compare the plan with the preferred-library standards: `lang-<language>-libraries`, `toolchain-api` for API styles, `aws-guidance` for AWS projects' Lambda and service-client work, else `toolchain-languages`. Prefer the repository's code, the standard library, the framework's features, then a listed library; write your own only for a named gap, and report each departure from a standard. A dependency the request did not name needs the user's approval.

MUST Keep one agent-readable engineering doc current in every repository: `docs/engineering.md` (see `architecture-docs-files`), linked from `AGENTS.md`. It records the stack (languages, toolchain versions, frameworks, key libraries and why), layout and dependency direction, standards with approved departures and their reasons, and how to build, test and lint. Read it before you work in the repo. A change that alters the stack (a new or removed dependency, a toolchain bump, a new crate or module, a new tool or a departure) updates it in the same PR; a reviewer treats a stale or missing doc as a finding. Report each departure from a listed library or practice, with its reason, in the report and the PR body.

MUST Put cross-cutting concerns (auth, validation, request ids, logging, tracing, metrics, error mapping, timeouts, retries, rate limits) in the framework's middleware, interceptors or decorators. Use one middleware model per surface: in TypeScript, Hono for HTTP APIs (Lambda included) and Connect for RPC; elsewhere ASGI/FastAPI, `net/http` wrappers or tower. `toolchain-api` compares Connect, gRPC and OpenAPI. Keep AWS Lambda handlers thin. Use Powertools for AWS Lambda in Python, TypeScript, Java and .NET when it fits an AWS project; Go and Rust use their runtime library, a structured logger and manual OTel. Instrument with OpenTelemetry over OTLP by default. `quality-code-design` has the rules in its `middleware.md` and `telemetry.md` references; each `lang-<language>-libraries` skill has the framework and SDK specifics.

MUST Use REUSE (`reuse annotate`, `LICENSES/`, `REUSE.toml`, `reuse lint` in CI) for per-file licence data instead of a custom licence guard. Keep a per-file licence exception at the file's boundary (its header or a narrow `REUSE.toml` path) and record third-party provenance in `NOTICE`. The `license-picker` skill's `references/reuse.md` has the setup.

MUST Scale planning and verification by uncertainty, consequences, and reversibility; file or line counts decide neither safety nor design. A PR request does not authorize a production release.

MUST Keep tests in step with the code, following the `quality-testing` skill (and `lang-<language>-testing` for idioms and tools): one behavior per test through the public interface, expected values worked out apart from the code, and a distinct risk per test, so search the existing tests and parametrize instead of copying. A refactor leaves tests unchanged; removed behavior takes its tests and fixtures in the same change. Never add a test that only checks removed code is gone, mirrors the implementation, re-checks what the compiler proves or exists for coverage, and never weaken an assertion or update a snapshot just to pass.

MUST Stub a dependency only when its contract exists and the implementation does not. With no contract, write the contract first; never invent the interface inside the stub. Never stub across a recorded decision (no "temporary" different library, engine or algorithm). Every stub is tracked work: no stub without a tracked swap task. In repositories that track work with bd, see the `beads-ledger` skill's `references/contracts-and-stubs.md` for the beads and edges. Design rules for writing a stub are in `quality-code-design`'s `contracts.md`.

MUST A swap replaces the stub with the real implementation, removes every `STUB(<task-id>)` marker, and proves that the real implementation passes the same conformance suite and that the consumer's tests pass against it. A swap that needs more than wiring exposes a contract gap: add a fixture that captures it to the contract in the same change. Before a release, no swap task is open, no `STUB(` marker remains in the tree (a CI grep, not a test), and every contract's staleness check passes.

MUST After an edit that spans files or changes a signature, run the project's type checker once through the shell before handing back, preferring its own script (`npm run typecheck`); `lang-<language>-quality` names the command.

MUST Refactor only within the requested change: fix the violations it introduces and report pre-existing ones. A major refactor needs the user's approval; a worker reports it to its lead instead of doing it.
